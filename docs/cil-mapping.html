Emerald to CIL

Every construct in the language, and what it becomes in a .NET assembly — separated into what the design already settles and what still needs deciding.

This document decides nothing. Where §3 or §5 determines a mapping it is recorded below with its source. Where nothing determines it, the question is stated with its options and my leaning, and left open. Written before any emit code exists, so that a mapping that refuses costs a paragraph rather than a rewrite.

Settled

Ten questions the design did not answer. Each changes the emitter's shape, and several change what a C# caller sees, so they were cheaper settled now than discovered later. All ten are now ruled on, against a stated preference for .NET compatibility and user-friendliness — which pull apart in exactly one place, question 01, and that one is decided for the beginner. Question 09 turned out not to need an encoding at all: the language rule it was trying to preserve was dropped instead.

01 Dictionary and Set cannot be the BCL types

This is the one that forces a decision rather than inviting one. §3.7 promises that a dictionary and a set keep insertion order, and the reasoning is explicitly pedagogical: a program whose output shuffles between runs is the worst thing to hand a beginner, because they cannot tell it from a bug of their own.

System.Collections.Generic.Dictionary<K,V> and HashSet<T> make no such promise. Their current implementations often appear ordered, which is worse than if they never were — it holds until a removal, then quietly stops.

  • Keep the promise. Emit an ordered implementation. A C# caller then receives an Emerald type rather than a familiar one, unless it implements IDictionary<K,V>.
  • Drop the promise. Use the BCL types directly, and delete the §3.7 rows.

Settled: keep the promise, and emit an ordered implementation implementing IDictionary<K,V> so most of the interop comes back. This is the single place where .NET familiarity and the teaching case conflict, and the teaching case wins: order is documented, demonstrated in examples/, relied on by the tour, and its whole reason for existing is that a beginner cannot tell shuffled output from a bug of their own. The BCL types are the worse trap precisely because they look ordered until the first removal.

02 What is List<T> at the boundary?

Emerald's list has about twenty methods — count, sum, map, filter, any?, find, join. The BCL's List<T> has Count, and the rest live in LINQ, which §3.7 deliberately does not auto-import.

  • It is System.Collections.Generic.List<T>, and Emerald's methods are extension methods the compiler resolves. Best interop; a C# caller gets a real List<T>.
  • It is an Emerald type wrapping one. Full control; every signature crossing the boundary carries a type C# does not know.

Settled: the BCL List<T>. It is the most common thing to hand across the boundary, and question 01 already spends the interop budget on Dictionary. This makes map and find extension methods that must not collide with LINQ's Select and First.

03 Int? and String? are different shapes in IL

One language feature, two representations. String? is a reference that may be null, carrying a nullability annotation the CLR does not enforce. Int? is Nullable<long> — a struct, with HasValue, that boxes when it meets object.

That difference reaches .or(), ?., and every generic instantiation: List<Int?> is List<long?>, and List<String?> is List<string> plus an attribute.

It also decides what nothing compiles to in a context where the type is not yet known — [nothing, nothing] is legal today and infers List<Nothing>.

Settled: follow the CLR rather than unify. C# lives with exactly this split and its users mostly never notice, because the compiler hides it. Unifying would box every Int?, which is the one thing a game engine will punish.

04 Does a struct box when it uses an operator trait?

struct Money with Addable is a CLR value type implementing an interface. Dispatching a + b through the interface boxes the receiver — on every addition.

Emerald never dispatches dynamically: overloads are resolved at declaration, there is no runtime metaprogramming, and the static type at every call site is known. So the emitter can always call the method directly and never touch the interface.

Settled: emit direct calls, and treat the interface as a compile-time contract that also happens to exist in metadata. Emerald never dispatches dynamically, so the static type at every call site is known and the receiver never boxes.

05 Should operator traits also emit op_Addition?

A C# consumer of Money sees an Add method and writes a.Add(b). It could just as easily see operator+ and write a + b. Emitting both costs one extra method that forwards.

§3.4's stated goal for the naming rules is that a C# consumer never learns Emerald was involved, which argues for emitting the operator.

Settled: emit both. It is cheap, invisible from Emerald, and §3.4's goal is that a C# consumer never learns Emerald was involved.

06 Does catch see .NET exceptions?

Half of this question has been answered since it was written, and the answer changed the other half. An Emerald error is no longer a compiler intrinsic: Error is an ordinary class declared in the prelude, a program derives its own with extends, and catch e: NotFound selects by type. So the CLR mapping for the Emerald side is the same one every class gets, with Error extending System.Exception and message an ordinary field.

What is left is the boundary, and typed catch sharpens rather than settles it:

  • Can a clause name a .NET exception — catch e: FileNotFoundException? The checker currently requires the named type to descend from Error, which no BCL exception does. Either interop types are admitted to that test, or System.Exception becomes the real root and Error sits under it.
  • An untyped catch e should still take everything, including an exception that came from .NET and has no Emerald message field. Mapping e.message onto Exception.Message covers it, which argues for the second option above.

Settled: make System.Exception the root, with Error the class Emerald programs extend and the one throw "text" builds. A bare catch then catches genuinely everything, and naming a BCL exception needs no special case.

07 Where does the assembly and namespace root name come from?

§3.3 maps directories to namespaces with the project as root, so Shapes.Dog becomes MyGame.Shapes.Dog. Nothing says where MyGame comes from.

  • The entry file's directory name — nothing to configure, but renaming a folder renames the namespace.
  • emerald.toml, which §3.5 already says appears on first need.

Settled: directory name by default, overridable in emerald.toml once that file exists for another reason. A student building a Windows executable should never meet a manifest.

08 What does the entry point look like?

The entry file's top-level statements become a static method that is the assembly entry point. Two details are unstated: whether it takes string[] args (there is no way to read them in the language yet), and how exit(code) reaches the process exit code — as a return value from Main, or as Environment.Exit.

Settled: emit static int Main(string[] args) — the parameter goes in now even though nothing in the language can read it, so adding argument access later does not change the signature. exit(code) throws an internal signal the entry point catches and returns, which is what the interpreter already does with ExitSignal.

09 What a subclass does to an inherited overload set

Answered by deleting the rule, not by encoding it. §3.2 used to say a subclass declaring a name replaced the base's whole set for it, so a Circle declaring draw() had no draw(Int) at all. C++ hides this way; C#, Java and Kotlin do not.

The decisive argument was this document's rather than §3.2's, though it is narrower than first written here. The rule was encodable. Emerald's own compiler resolves Emerald calls and could enforce hiding while emitting ordinary IL; a method inherited in metadata does not have to be reachable from Emerald source. What could not be had was one answer. A Circle emitted to IL inherits Draw(int), so a C# caller sees a sibling an Emerald caller does not, a method group converted on each side resolves differently, and a call through a Shape reference reaches a virtual method the Emerald rule says is absent. Two lookups either side of the boundary, for a rule no one had asked for.

So the rule was dropped in the language instead. An own method now replaces the inherited one taking the same parameters and leaves its siblings reachable, and override became a claim about one signature rather than about a name. The emitter has nothing special to do: ordinary virtual dispatch is now what Emerald means.

Settled: no encoding needed. The one thing worth recording is how it was found — the question came from an outside reading of a row sitting in the settled column, and what it exposed was not an encoding problem but a rule whose cost was two lookups and whose benefit nobody could name.

10 What is a func(...), and what is a method value?

New. §3.1 removed optional parentheses so that rex.speak could be the method rather than its answer, which means the emitter now has to produce something for a member read that names a method — a thing the tree-walker answers with a BoundMethod object and IL has no equivalent for. Two decisions, and the second is the awkward one.

  • What type is func(Int): String? Either the BCL's Func<int, string> and Action<…> family, or a delegate type emitted per signature. The BCL types are what a C# caller expects and what every library takes, and they cost nothing to consume; against them, they stop at sixteen parameters, they split into two families over whether anything is returned — a split Emerald does not have, since func() is one shape — and ref/out have no spelling in either.
  • How is a method value emitted? ldftn plus newobj on the delegate, which is exactly C#'s method-group conversion, so the shape is not in doubt. What is in doubt is which method, when the name is overloaded: the checker picks the overload from the expected type and the runtime keeps the whole set and dispatches on the arguments, which agree today only because the checker refuses any expression where they would not. An emitter has to record the checker's choice on the AST rather than rediscover it, and nothing currently does — the interpreter never needed it.

This meets question 09 head-on. If a subclass hides an inherited overload set, then circle.draw as a method value has to resolve against Emerald's view of the set and not the CLR's, and a C# consumer converting the same method group would get the other answer.

Settled: the BCL Func<…> and Action<…> families, for the same interop reason as question 02, accepting that a seventeen-parameter function is not a language anyone needs. A method value is ldftn plus newobj, which is C#'s own method-group conversion. The one piece of work this creates is not a question: the checker has to record which overload it chose on the AST, because the emitter cannot rediscover it and nothing stores it today — the tree-walker kept the whole set and picked on the arguments, which IL cannot do.

Notes and risks

Not decisions, but things that will bite during phase 2 if they are met by surprise.

— Three conformance vectors, and what they are for

The interpreter is the specification of Emerald's runtime behavior, and the only copy of it. Every risk on this page has the same shape: the emitter reaches for the obvious BCL call or CIL opcode, that call has C#'s semantics, and C#'s semantics are not always Emerald's. The disagreement is silent — both versions run, and one of them prints a different number.

So three golden cases exist to be the emitter's acceptance suite rather than to demonstrate a feature: conformance_arithmetic (the four-sign floored division matrix, / always producing a Float, rounding, truncation, the Int64 boundaries, float printing), conformance_ordering (one comparer, ordinal, agreeing with the operators; insertion order for dictionaries and sets), and conformance_overload_selection. They pass against the interpreter today, and they are an initial baseline rather than a finished bar. A fourth has since joined them: conformance_evaluation_order pins order and count rather than values — which subexpression runs first, and which does not run at all. A backend can get every value right and still emit control flow that evaluates an operand it should have skipped, and no test checking only the answer would see it, so every line there prints as a side effect and the transcript is the assertion. Three more have joined since: conformance_overflow (the checked opcodes, the Int64 edges, and Float saturating to infinity instead of reporting), conformance_equality (what == means per kind — the emitter has three plausible things to reach for at every comparison), and conformance_closures. That last pins the mistake C# shipped for five versions: a lambda in a loop must capture the variable per turn, not share one, and 1 2 3 rather than 3 3 3 is the whole test. Two more since: conformance_construction_order and conformance_exceptions. The first is the one most likely to be got wrong by copying the host, because C# and Java do not agree with each other — C# runs the derived field initializers, then the base ones, then the base constructor; Java runs the base constructor before any derived initializer, which is why a derived field read from an override called out of a base constructor is null there and not in C#. Emerald does neither: every field initializer runs, base first, before any constructor body, so by the time a constructor body executes every initialized field in the whole object holds its value. That is what makes the construction-safety rules coherent, and an emitter following C# out of habit would break it. Module initialization turned out to be covered already, by module_init — and testing the case it did not reach found a defect rather than a gap, since fixed. §3.3's rule stopped holding as soon as one module's top-level code named another: a module reached only from inside another module's initializer ran before the entry file executed a single statement. The cause was a split. §3.3 turns a file into members and an initializer, and a top-level var went into members — where it was treated as a class's static var and evaluated when the type was declared. So a module file ran half at startup and half on first access, and the half that ran early dragged in whatever it named. A top-level var is top-level code; it now waits with the rest of the file, and the two lists are merged back by line rather than appended, because a print above a var and a print below it are different programs. Pinned by module_init_stays_lazy and module_var_order

Writing them found two more disagreements, which is now the reliable yield of this exercise. A block lambda that returned a value was typed as giving back Unknown, so its returns were checked against nothing and any value passed — and once unknowns stopped satisfying declared types, var f: func(): Int = { ... return x } was rejected outright as a func() that gives nothing. The type the position asks for is the only thing that can say what a block's returns must be, since a block has no single expression to read one from; taking it fixes the rejection and starts checking the returns.

The second was 1 == 1.0 answering false while 1 <= 1.0 and 1 >= 1.0 both answered true — the ordering operators treating Int and Float as one number line, which is what makes 1 < 2.5 work, and equality comparing type-strictly. Those cannot both be right, and a reader can derive the contradiction in three lines. Same shape as sort disagreeing with <, and found the same way. Settled toward the languages a student arrives from: == is now numeric across the pair, as it is in Python, Ruby, C# and JavaScript. Only the mixed pair converts, since widening two Ints would make the two largest compare equal; and set membership and dictionary lookup stay refused across types, because a hash cannot be made to agree the way a comparison can. Zero existing cases moved, which by now is the expected result rather than a reassuring one — the corpus had never once compared an Int with a Float. The backend is ready when it passes these unchanged and the list above has been written.

Two were written after finding something. round is away from zero and Math.Round is not — .NET rounds a midpoint to even, so Math.Round(2.5) is 2 where Emerald says 3, and an emitter reaching for the obvious call would have silently changed every .5 in every program. And sort disagreed with <: it used Comparer<object>.Default, culture-sensitive for strings, so ["b", "A", "a", "B"].sort() gave a, A, b, B while "a" < "B" answered false. That one was already wrong before any backend existed, and locale-dependent besides — the same program printing different output on a different machine, which is precisely what §3.7's ordering promise exists to prevent. Fixed by giving sort, sort_by, min, max, min_by and max_by the one comparer the operators already used.

— Overload selection cannot diverge, and that is a guarantee worth having

The interpreter picks an overload from the runtime values it holds. Emitted IL will pick from the static types at the call site. In C# those rules disagree: a Dog held in an Animal variable calls the Animal overload, where a runtime-dispatching interpreter would call the Dog one.

An earlier revision of this page said no Emerald program could express the disagreement, on the strength of four overlap shapes being rejected where they are declared. That was an overclaim, and testing the rest of the surface broke it three times. The invariant worth stating, because it can be tested rather than asserted: every call the checker accepts selects the same declaration the interpreter invokes.

It failed for an overload inherited from a base and reached through a base reference, where static resolution binds to the base's version and the interpreter found the subclass's. And it failed twice in ways that were unsound with no backend involved — the interpreter's matcher discriminated on neither a block's parameter count nor a list's element type, so var answer: String = run_it({ n => n + 1 }) put an Int into a variable declared String.

One root cause, not three: the checker and the interpreter each reconstructed the decision from different information, and the interpreter's copy was a hand-written match found missing Pair, function shapes, block arity and list elements — every time by someone looking, never by a test failing. The list case proved a fifth patch could not work. A runtime list carries no element type and an empty one has nothing to inspect at all, so the checker's answer is not reconstructible from values in hand even in principle.

So there is now one decision. A signature carries the declaration it was read from — outside equality, since two signatures are the same type whoever wrote them — the checker records which declaration each call resolved to, and the interpreter invokes that one. The three cases became overload_through_a_base_reference, overload_chosen_by_block_arity and overload_chosen_by_list_element. The emitter wants exactly this record, so resolving statically is now reading the checker's answer rather than a third reconstruction of it.

— The shipped runtime library, and what is left of it

The structural blocker, as against the semantic ones. §5.4 speaks of a shipped runtime library; until recently there was none. The sixty-seven built-in methods live in Builtins.cs, which takes an Interpreter and a List<object?>, and emitted CIL can call none of it. A backend built against that layout would reimplement string and collection behavior — and every divergence on this page would recur, one method at a time, in a second copy that nothing diffs against the first.

The coupling is shallower than the signature suggests, and the first slice now exists. Emerald.Runtime is a separate project holding rounding, floored division, float formatting and the one comparer; the compiler references it and never the reverse. tests/runtimecaller is a plain C# program that references the runtime and nothing else — so a rule the backend needs cannot drift back into the compiler without that failing to build. A reference list enforces the boundary; discipline does not. Every call in it is a static method on a plain type taking plain values, which is the shape emitted CIL can call directly.

Extracting it found a bug immediately, which is the argument for doing it before the emitter rather than alongside. Floored integer division was computed as Math.Floor((double)a / b) — correct up to 253 and silently wrong above it, so 9223372036854775807 // 3 came out as 3074457345618258432, off by 170. Done in integers it is exact. A backend emitting the same shortcut would have inherited the same wrong answer, and the two would have agreed with each other while both being wrong.

The callback surface, and how much of it turns out not to exist. Thirteen built-in sites re-enter Emerald code, and the first guess — that they were the block-taking ones — was too narrow. Eight take a block; five reach a value's own method by name: equals? behind every ==, compare behind every ordering, at and set_at behind every index, and to_string behind every print and interpolation.

They are two shapes, not thirteen, and only one of them is a decision.

A block is a delegate. There is nothing to choose: a compiled Emerald lambda already is a CLR delegate, so emitted code passes one with no adapter. The interpreter is the side that has to wrap, because its own block is an ICallable whose Call takes an Interpreter — precisely the calling convention that must not travel into a shipped library. Collections.SortBy is now in the runtime taking a plain Block delegate, with the interpreter wrapping at the one call site and the C# caller passing a lambda directly. That settles the eight.

A value's own method is mostly not a callback at all, which is the finding worth having. It is one only because the interpreter represents a user object as an EmInstance — a dictionary of fields with no methods on it, and no reference to the interpreter that could run them. An emitted class has none of that problem: it is a real CLR type with a real ToString override, so print in compiled code is a virtual call the CLR dispatches, and == is an Equals override. The re-entry exists on one side of the boundary and evaporates on the other.

So the shape to aim for is an interface the runtime programs against, which an emitted class satisfies natively and EmInstance satisfies by delegating — not a hook. The thing to remove is Builtins.Stringify, a static mutable Func that whichever Interpreter was constructed last installs at startup: a process-wide singleton, wrong for a compiler that may hold two programs, and impossible to emit against. That replacement is the next decision due, and it is deferred rather than guessed at here, because the choice between an interface on the value, an interface on the host, and a per-call delegate changes what a C# consumer of an Emerald assembly sees.

— // and % floor; div and rem truncate

The one found by asking what the emitter would do rather than by reading the code. Emerald's integer division and remainder are Python-style, floored, deliberately and with a stated reason — -7 // 2 is -4 and -7 % 2 is 1, so n % 2 == 1 detects an odd number whatever its sign. CIL's div and rem truncate toward zero, which is C#'s rule and gives -3 and -1.

The emitter must not reach for the obvious instruction. Nothing would catch it if it did: the golden tests run the interpreter, so the suite would stay green while every negative division in every compiled program changed its answer. This was settled and tested in operators.em, and it was recorded in a comment inside a test file — nowhere a person writing the code generator would look.

Confirmed as the intended behavior rather than an accident. The interop argument does not apply: % is an in-language operator and never crosses the boundary, so a C# consumer never learns which rule was used. The cost is a few extra instructions and a moment of surprise for a C# reader, against a beginner writing if n % 2 == 1 and being right.

— String iteration is by text element, not by char

for letter in "héllo" yields real characters — the tour and the examples both promise that é is one turn of the loop and a family emoji is one. .NET's string enumerates UTF-16 code units, which is neither. This needs StringInfo / TextElementEnumerator, and it is easy to emit the fast wrong thing by accident because the fast wrong thing is what foreach (char c in s) does.

— The environment may block a freshly emitted assembly

Smart App Control already blocks the compiler's own build on this machine, which is why everything runs under WSL with -p:UseAppHost=false. An assembly the compiler writes and then tries to execute is a new instance of the same class of problem, and it will look like a compiler bug when it is not. Worth provoking deliberately, early, on a trivial assembly — before there is enough emitted code for the failure to be ambiguous.

— Two implementations, and one of them is the oracle

Once the backend runs anything, every golden test becomes a differential test for free: the same program through the interpreter and through the assembly must print the same thing. That is worth wiring up on the very first program that compiles, rather than after the emitter is large enough to have opinions.

What it cannot see is semantics that are wrong consistently — the emitter will be written by reading the interpreter, so a shared mistake stays invisible. That is the gap the combination pass exists to cover, and the reason it comes first.
