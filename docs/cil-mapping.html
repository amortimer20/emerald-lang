Emerald to CIL

Every construct in the language, and what it becomes in a .NET assembly — separated into what the design already settles and what still needs deciding.

This document decides nothing. Where §3 or §5 determines a mapping it is recorded below with its source. Where nothing determines it, the question is stated with its options and my leaning, and left open. Open

Eight questions the design does not answer. Each changes the emitter's shape, and several change what a C# caller sees, so they are cheaper settled now than discovered later.

01 Dictionary and Set cannot be the BCL types

This is the one that forces a decision rather than inviting one. §3.7 promises that a dictionary and a set keep insertion order, and the reasoning is explicitly pedagogical: a program whose output shuffles between runs is the worst thing to hand a beginner, because they cannot tell it from a bug of their own.

System.Collections.Generic.Dictionary<K,V> and HashSet<T> make no such promise. Their current implementations often appear ordered, which is worse than if they never were — it holds until a removal, then quietly stops.

  • Keep the promise. Emit an ordered implementation. A C# caller then receives an Emerald type rather than a familiar one, unless it implements IDictionary<K,V>.
  • Drop the promise. Use the BCL types directly, and delete the §3.7 rows.

Leaning: keep it. The promise is load-bearing for the teaching case and it is already documented, demonstrated in examples/, and relied on by the tour. Implementing IDictionary<K,V> over an ordered store recovers most of the interop.

02 What is List<T> at the boundary?

Emerald's list has about twenty methods — count, sum, map, filter, any?, find, join. The BCL's List<T> has Count, and the rest live in LINQ, which §3.7 deliberately does not auto-import.

  • It is System.Collections.Generic.List<T>, and Emerald's methods are extension methods the compiler resolves. Best interop; a C# caller gets a real List<T>.
  • It is an Emerald type wrapping one. Full control; every signature crossing the boundary carries a type C# does not know.

Leaning: the BCL type. List<T> is the most common thing to hand across the boundary, and question 01 already spends the interop budget on Dictionary. Note this makes map and find extension methods that must not collide with LINQ's Select and First — which §3.7 has already thought about.

03 Int? and String? are different shapes in IL

One language feature, two representations. String? is a reference that may be null, carrying a nullability annotation the CLR does not enforce. Int? is Nullable<long> — a struct, with HasValue, that boxes when it meets object.

That difference reaches .or(), ?., and every generic instantiation: List<Int?> is List<long?>, and List<String?> is List<string> plus an attribute.

It also decides what nothing compiles to in a context where the type is not yet known — [nothing, nothing] is legal today and infers List<Nothing>.

Leaning: follow the CLR rather than unify. C# lives with exactly this split and its users mostly never notice, because the compiler hides it. Unifying would mean boxing every Int?, which is the one thing a game engine will punish.

04 Does a struct box when it uses an operator trait?

struct Money with Addable is a CLR value type implementing an interface. Dispatching a + b through the interface boxes the receiver — on every addition.

Emerald never dispatches dynamically: overloads are resolved at declaration, there is no runtime metaprogramming, and the static type at every call site is known. So the emitter can always call the method directly and never touch the interface.

Leaning: emit direct calls, and treat the interface as a compile-time contract that also happens to exist in metadata. Worth confirming early, because if it does not hold, struct plus operator traits is a performance trap sitting under the most natural way to write a vector type.

05 Should operator traits also emit op_Addition?

A C# consumer of Money sees an Add method and writes a.Add(b). It could just as easily see operator+ and write a + b. Emitting both costs one extra method that forwards.

§3.4's stated goal for the naming rules is that a C# consumer never learns Emerald was involved, which argues for emitting the operator.

Leaning: emit both. It is cheap, it is invisible from Emerald, and it is the difference between a library that feels foreign and one that does not.

06 What is an Emerald error, and does catch see .NET exceptions?

throw "text" and throw Error("text") both work, and catch e is untyped in v0. Two questions follow that the tree-walker never had to answer, because it had no BCL beneath it.

  • What CLR type is thrown? Presumably one EmeraldError : Exception, so e.message has somewhere to live.
  • When Emerald calls into .NET and .NET throws — a FileNotFoundException, say — does catch e catch it? If yes, e.message must work on any Exception. If no, a program can be killed by something it visibly wrapped in a try.

Leaning: catch everything, and give e.message the underlying Exception.Message. A try that visibly fails to catch is the worse outcome, and typed catch is already deferred to when user-declared error classes exist.

07 Where does the assembly and namespace root name come from?

§3.3 maps directories to namespaces with the project as root, so Shapes.Dog becomes MyGame.Shapes.Dog. Nothing says where MyGame comes from.

  • The entry file's directory name — nothing to configure, but renaming a folder renames the namespace.
  • emerald.toml, which §3.5 already says appears on first need.

Leaning: directory name by default, overridable in emerald.toml once that file exists for another reason. A student building a Windows executable should never meet a manifest.

08 What does the entry point look like?

The entry file's top-level statements become a static method that is the assembly entry point. Two details are unstated: whether it takes string[] args (there is no way to read them in the language yet), and how exit(code) reaches the process exit code — as a return value from Main, or as Environment.Exit.

Leaning: emit static int Main(), and let exit(code) throw an internal signal the entry point catches and returns — which is exactly what the interpreter already does with ExitSignal, so the semantics are already decided and tested.

Notes and risks

Not decisions, but things that will bite during phase 2 if they are met by surprise.

— String iteration is by text element, not by char

for letter in "héllo" yields real characters — the tour and the examples both promise that é is one turn of the loop and a family emoji is one. .NET's string enumerates UTF-16 code units, which is neither. This needs StringInfo / TextElementEnumerator, and it is easy to emit the fast wrong thing by accident because the fast wrong thing is what foreach (char c in s) does.

— The environment may block a freshly emitted assembly

Smart App Control already blocks the compiler's own build on this machine, which is why everything runs under WSL with -p:UseAppHost=false. An assembly the compiler writes and then tries to execute is a new instance of the same class of problem, and it will look like a compiler bug when it is not. Worth provoking deliberately, early, on a trivial assembly — before there is enough emitted code for the failure to be ambiguous.

— Two implementations, and one of them is the oracle

Once the backend runs anything, every golden test becomes a differential test for free: the same program through the interpreter and through the assembly must print the same thing. That is worth wiring up on the very first program that compiles, rather than after the emitter is large enough to have opinions.

What it cannot see is semantics that are wrong consistently — the emitter will be written by reading the interpreter, so a shared mistake stays invisible. That is the gap the combination pass exists to cover, and the reason it comes first.
