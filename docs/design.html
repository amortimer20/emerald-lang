§ 1Position

Emerald exists because two languages the author admires each solve half the problem. Ruby is expressive but resists tooling. C# is robust but greets a fourteen-year-old with public static void main.

Emerald is a statically typed, object-oriented language compiling to CIL. It has two audiences that most languages treat as mutually exclusive:

A student's first language. Line 1 of a file is real code. Every character on screen day one can be honestly explained day one. No ceremony deferred to a later unit, no "ignore this for now."

A working language. Full access to .NET, real tooling, real performance, and the ability to build libraries and wrap engines — not a toy that students outgrow in a semester.

The bet holding these together is that the ceremony most languages impose is not load-bearing. C#'s boilerplate is not what makes C# powerful, and removing it costs nothing but familiarity.

There is a sharper way to state the goal, which took most of the design conversation to surface. Ruby's celebrated expressiveness was, in large part, DSL-ability — has_many :comments and validates :email, presence: true read like language features because Ruby let libraries behave like language. Rails did not feel like a framework; it felt like a dialect. That is the thing worth taking, and it is also precisely what Ruby paid for with runtime metaprogramming, and therefore with its tooling. Same feature, both sides of the ledger.

So Emerald is Python's small regular surface, plus Ruby's library-as-language, minus the runtime magic that made the second one expensive. Which reframes the compile-time-only constraint (§2.3): it is not a compromise accepted for tooling's sake, it is the enabling condition. A macro expands into real declarations the compiler and the LSP can see — jump-to-definition works, autocomplete works, the expansion can be inspected. method_missing offers none of that; it is a promise that something might exist. That difference is what makes a DSL-friendly language buildable rather than merely dynamic.

Origin of the idea

The immediate motivation is teaching game development. Unity's engine model is the one the author finds clearest to teach; Unity's C# API is the part that gets in the way. GDScript reads better not because it is a better-designed language, but because it is fused with its engine. Emerald's thesis is that this fusion is achievable as a library plus compile-time metaprogramming — not as a bespoke engine language.

§ 2Principles

Six rules derived during design. Each one settles a class of future arguments, which is the only reason to write principles down.

2.1

Small core, generous library

The grammar fits on two pages; the standard library does not. Ruby's upto and each are library methods, not syntax — Ruby's grammar was never the large part. This is how Lua's learnability and Ruby's expressiveness stop fighting each other.

2.2

A new spelling is free; a new concept is a tax

Two ways to write a statement with identical semantics costs a student thirty seconds. Two ways to introduce a variable with different rules costs them a mental model. unless is welcome. C#'s var-alongside-int is not.

The sharper test, arrived at when this principle had to explain its own past decisions: can a student derive it from what they already know? unless is if not — one sentence and they have it, and it desugars away before the checker ever sees it. Ruby's case/when is not derivable: when 5 matches by value, when Integer by class, when 1..10 by containment, three behaviors from identical-looking syntax. That is a rule you must be taught. ** passes because the concept comes from maths class; // passes because it paid for itself, letting / stop lying about 7 / 2.

2.3

Domain feel comes from macros, not from grammar

@export is not a keyword — it is a compile-time attribute, lowering to a .NET one. Domain-specific expressiveness is bought in libraries, so the core language never grows to pay for it. Overstated as written, and corrected here rather than left standing. This called itself the load-bearing feature of the design, and the accounting does not support it: §3.8 harvested four demands, three are attributes and shipped, and the fourth — assert — turned out to need only the syntax tree, not a macro system. §3.8's own closing row reaches the same place from the other direction: what makes the Unity sample read like GDScript is the block-free class line, trailing lambdas, inference, func and snake_case, every one of them settled grammar. The principle is sound and its mechanism was misidentified: expressiveness is bought without growing the core, but by choosing grammar general enough that libraries need not extend the language — not by letting them extend it. Corrected: this principle called @export a macro until §3.8 split attributes from macros and found they were never one mechanism — attributes are declarative and generate no code, macros are function-like and in expression position, and assert is the only one of the four harvested demands that is actually a macro. The heading keeps the word "macros" because the argument it makes — domain feel is bought in libraries, not paid for in grammar — holds for both.

2.4

There is always a blessed default

One formatter with no configuration. One build tool, test runner, and package manager, in the box. Alternatives may exist; they are not equal. The complaint about the Node ecosystem is not complexity — it is the absence of a default.

2.5

Prefer the reversible choice

Where a decision is close, start on the side that can be changed later. Adding an implicit lambda parameter later is backward compatible; removing one is not. Reversibility breaks ties that reasoning cannot.

2.6

Warnings are pedagogy

The compiler is the most patient teacher in the room. Diagnostics should name the practice, not just the fault — and point at the line where the mistake was made rather than where it surfaced.

§ 3Settled decisions

Decided during design conversation. Reasoning is compressed to the deciding argument — the thing that would have to change for the decision to change.

3.1Lexical and syntactic

DecisionFormDeciding argument
Block delimitersBracesWhitespace sensitivity forbids inline blocks, which the entire library-not-grammar thesis depends on. Python has no multi-statement lambda for exactly this reason.
Brace styleStroustrupAn opening brace ends its line, a closing brace begins one, and else is never cuddled. One invariant covering statements and lambdas alike — which Allman could not manage, since a newline before an expression-position { is ambiguous. Isolates } else {, the line where the novice confusion actually lives.
Comment syntax# line, ## doc, #[ … ]# blockForms are distinguished by the character following the hash, never by counting hashes. Because doc content is markdown, a student typing ### TODO out of markdown habit must not silently open a block that swallows code to end of file. Beats Ruby's =begin/=end, which is unused because it is ugly.
Doc comment contentMarkdown, with @param and @returnsNot a second syntax — this is what goes inside ##. Javadoc's @param duplicates the signature and goes stale; types come from the compiler, and tags carry only what it cannot know. Half of that was wrong, and the row had never been built at all. ## and # went down the same path in the scanner and were both skipped to end of line, so the 413 doc comments in the corpus were decoration: nothing read them, no tag was parsed, nothing was emitted. The reasoning was right about types and wrong about meaning — that a radius is measured from the center, and must be positive, is not in the signature and never will be. And "goes stale" is not a property of the idea, it is a property of Javadoc: C# verifies <param> names against the signature and warns, which is why its docs rot less. Emerald now does the same.
Two tags, and four things inferred@param, @returns, nothing elseThe summary is the first paragraph, the remarks are what follows it, an example is a fenced code block, and <inheritdoc/> falls out of a member being an override with no doc of its own — none of those needs a tag, because the compiler can see all four. What it cannot see is which parameter a sentence is about and what the answer means, so those two are written. @throws was proposed and cut: Emerald throws strings rather than types, so <exception cref="..."> would have nothing to point at, and "throws when the canvas is disposed" reads perfectly well as prose. §2.5 settles the direction — adding a tag later is backward compatible, removing one is not.
A mismatched tag warnsAnd an undocumented parameter says nothingThe program is correct and only the comment is wrong, so it is a warning, not an error — and the suggestion machinery already in the checker turns @param raduis into did you mean radius? without any new code. Deliberately narrower than C#, which also warns when a parameter is left undocumented. That would fire on every partly documented function in a codebase, and a warning that fires constantly is one a reader learns to skip — which is the opposite of what §2.6 asks a diagnostic to be. Documenting nothing is silent; documenting something wrongly is not.
Why source stays markdownIntelliSense reads the emitted file, not the commentThe question that prompted this was whether ## should adopt C#'s XML to get IntelliSense, and the answer is that the two are unrelated. A .NET library ships Foo.dll beside Foo.xml and the IDE reads the XML; nothing looks at the source. So the comment syntax and the metadata format are independent, and Emerald can keep markdown and emit the XML that tooltips want. Writing <summary> to deliver four words is C#'s worst ergonomic feature and precisely what a fourteen-year-old should not meet on line 1. The emitting half waits on the code generator; the capturing and checking half does not, which is why it shipped first.
Attributes@name sigilReads better than [Brackets], and gives macros one surface. @ uniformly means "metadata about the thing attached."
String interpolation"#{expr}", no prefixA required prefix fails silently when forgotten — the student sees literal braces and cannot tell why. ${} was reconsidered on the grounds that C# prefixes strings with $, and rejected: C# is $"...{name}", where the sigil is on the literal and the hole is bare, so copying ${} imports JavaScript's syntax while thinking of C#'s. And since every string here interpolates, the sigil has to be rare immediately before a brace — ${ is common in shell, JS templates and property placeholders, where #{ is confined to Ruby and Sass. # is also already this language's meta-character, for comments; adopting $ would make two where one does.
Escaping an interpolation\#{ }There was no way to write #{ as text — \#{name} interpolated anyway. The scanner did handle the escape, but interpolation is split later, in the parser, and by then an escaped hash was indistinguishable from a real one. The scanner now leaves \# and \ escaped, and the parser undoes them where it can still tell the difference. A bug that needed a program printing Emerald source to notice — a code generator, or a tutorial about this very syntax.
Boolean operatorsnot and or onlyRuby's and and && have different precedence, a famous footgun. One set makes the bug unrepresentable.
Ranges1..5, inclusiveReads aloud correctly; pairs with the iterator protocol.
A range counts up5..1 is empty, not reversedIt used to reverse itself, and that was never decided — this row said only "inclusive", and the descent was an artifact of the enumerator. Choosing an inclusive range is what obliges the question to be answered. With an exclusive one, walking an empty collection is 0..<0, which is empty because it says so; inclusive means "walk n items" has exactly one spelling, 0..(n - 1), so n == 0 gives 0..-1. The backwards case is not an exotic mistake there, it is the unavoidable consequence of the choice above, and reversing made the commonest loop in programming index out of bounds on the commonest edge case. Found by writing a game board: 0..(count - 1) over an empty list yielded {0, -1}. Ruby and Python arrive at empty by different routes — Ruby puts direction in a method name, Python in a third argument — and agree exactly here: (5..1).to_a is [] and range(5, 1) is empty.
upto and downtoNow each means its own directionThey were one function. Both built a range and walked it, so the range's own direction decided what happened and neither name constrained anything: 3.upto(1) counted down and 5.downto(9) counted up. Which means the language had no descending mechanism at all — one behavior under three spellings, two of them decorative — and the reason that went unnoticed is that nobody had asked either name to do the thing it is named after. With a range ascending, upto is honest for free and downto is now the one construct in the language that counts down. Ruby's semantics exactly, arrived at from the other end.
Written backwardsRefused; worked out, it stays quietfor i in 10..1 is a countdown that does nothing, and doing nothing silently is the failure §2.6 exists to catch. But 0..(n - 1) must stay quietly empty, because there the emptiness is the answer — the whole point of the row above. The distinction is exactly what a checker can see: whether both ends are written out or computed. §3.1's pattern for a syntax corner, applied again — add a message, not a rule.
No stepdownto carries itPython's third argument is the other way to spell direction, and it is a third operand on a construct with two — §2.1's line, where the library carries what the grammar should not. Ruby declines it too, and more firmly: (1..5).step(-1) raises rather than reversing, so neither language lets a step decide direction. If a step is ever wanted it is (1..10).step(2), a method, and it is not wanted yet.
unlessThe negated twin of if, desugared in the parserunless becomes if not, so nothing downstream learns it exists. Expression-level choice, free by §2.2, and it reads better than the negation it replaces. It had a twin, until, and the twin is cut — see below. unless survives on evidence the other one could not produce: 21 uses across the corpus, 14 of them as a trailing guard.
unless takes no elseAn error, with the fix suggestedRuby permits it and every style guide bans it: "unless x … else …" is a double negative nobody parses correctly first time. Also warns on unless not x.
until is cutThree appearances, all of them until testing itselfThe first thing removed from the language rather than added to it, and the audit that found it is repeatable: count every keyword's real uses across the corpus with comments and string bodies stripped. until came back with three, and all three were self-referential — the example demonstrating until, the golden case testing until, and the error case for the rule until required. Not one program ever chose it. unless, its twin, came back with 21. And it cost more than a keyword. §3.1 carried a rule — modifiers guard, they do not loop — whose whole job was refusing n += 1 until done, with an error case and a diagnostic behind it. Removing the keyword retires the rule, because there is no longer a looping modifier to refuse. A keyword, a production, a rule a student had to be taught, and a reserved word nobody could name a variable after — spent on a spelling of while not that nobody wrote. The counter-argument is real and lost anyway: until countdown.zero?() does read better than the negation, and Ruby has it. Reading better is not the same as being reached for.
Modifier formsprint(x) if cond, same line onlyExpression-level choice — free by §2.2. The same-line rule was implicit in the continuation rules (if is not among the tokens that continue a statement) and is now explicit, because otherwise a following if on its own line is ambiguous between a modifier and a new statement.
No trailing lambda in conditionsParentheses requiredSurfaced by writing the grammar (§9). if x { ... } is genuinely ambiguous — expr { ... } is the trailing-lambda form, so the block could attach to x. Kotlin hits this exactly and resolves it the same way: if (items.any? { p => p.valid? }) { ... }. Applies to if and while conditions and the for iterable.
Assignment is a statementNever an expressionSo if x = 5 { } is a syntax error rather than a silent bug — the classic C-family disaster where = is typed for == inside a condition, assigns, and evaluates truthy. Eliminated structurally instead of by a warning. Costs only while (line = read())-style idioms, which are unwanted here anyway.
Compound assignment+= -= *= /=Passes the §3.7 sprinkle test: removes a repetition where the variable name otherwise appears twice, which is a real source of typos. Lowers through the operator traits — x += y becomes x = x.add(y).
No ++ or --RejectedThe pre- versus post-increment distinction exists for reasons no beginner needs, generates exam questions that test nothing useful, and makes expressions like i++ + ++i possible. count += 1 is one character longer and has no subtleties. Ruby made the same call and nobody misses them.
No bare blocks{ } is never a statementEmerald has no need for anonymous scopes, and forbidding them means a { following an expression is always a trailing lambda. Previously undecided; the grammar forced it.
Three if forms parse cleanlyParse the condition, then peek{ means statement, then means expression. No grammar rule needed for the corner cases — if cond then x without an else is the error a student will actually hit, and it is answered with a diagnostic (§4.4) rather than a restriction. The pattern for syntax corners in a teaching language: add a message, not a rule.
Conditional expressionif cond then a else b; no ternaryMaking if an expression yields a smaller language: the alternative is a statement if plus ?:, which is two constructs where this is one. Ruby precedent — if x then y else z end is valid there, and its ternary is the C inheritance sitting awkwardly beside it.
Why then, not bracesBlocks never carry valuesRust's brace form requires blocks to yield their last expression, which is implicit return — rejected in §3.2. then buys the feature without touching block semantics, and its single-expression limit is a teachable boundary: multi-statement branches use the statement form. Also closes the newline-before-else wrinkle, since { versus then tells the parser which form it is in.
ParenthesesRequired for every callReversed. They were optional when nothing was passed, on the rule if it needs information, put it in parens — decidable at every call site without knowing the implementation. What that rule cost was not discovered until callbacks were tried: if reading a member gives you its result, no member read can give you the function, so connect(self.on_pressed) is unwritable and rex.speak silently runs the method. Uniform access and first-class methods are the same slot, and only one thing fits in it. A game-engine handler is the first callback a student meets, which decides which one this language wants. The narrow fix — paren-less only for ? names, since empty?() reads badly — was rejected for buying the inconsistency without the feature: check(rex.hungry?) would still invoke, so a whole naming class stays unreferenceable and there is now an exception to teach. Two spellings for one call had also already put both in the corpus: .upper and .upper() both appear across the .em files, written by the same author in the same week.
What replaces itFour lines, no exceptionso.name reads a field, a property, or a method value; o.name() invokes it; o.name(args) invokes it with arguments; a bare exit is a value, not a call. Every call has parens and every paren-less dotted name is a read — which is one rule rather than a rule plus the list of names it does not cover.
Bare names in statement positionNo longer a callWithdrawn with the rule it came from. exit alone had been made to mean exit(), so that members and bare names would not disagree; with parens required, they agree by saying nothing. It is not silent, because the row below catches it: exit as a statement now reports that it does nothing, and the fix it names is the (). The positional carve-out — a call in statement position, a value in expression position — disappears with it, and that is the better outcome: one name meant two things depending on where it sat.
Statements that do nothingAn error, and now load-bearingWas the second half of the bare-name bug; is now the whole safety net. A statement that computes a value and discards it is nearly always a typo, so total, a + b and — the case that matters after this change — rex.speak without its parens are rejected. That last one is the mistake this change creates, so it is the one the diagnostic has to name well: the value is a func(): String and nothing was done with it. This is the "unused expression" lint §3.1 once listed as a cost of optional parens, now the thing that makes their removal safe.
What this does to propertiesWhere uniform access wentNot lost, moved. A var with a get body (§3.4) is still indistinguishable from a stored field at the call site, so promoting one to the other still never breaks callers — the interchange that mattered survives intact. What ends is the third member of that set: a zero-argument method is no longer interchangeable with them. That is a real narrowing, and it is the price. It also hands the choice to the library author, in the shape the author is best placed to answer: is this a value the object has, or an operation it performs? The rejected property/method split asked a harder question — whether arr.sort copies or mutates — and that one is still unanswerable from the call site, which is why it stays rejected on its own terms.
One name for "how many"count, on every type that can be askedFound while defending the row below, and the more valuable half of it. A String answered only to length while every container answered only to count — two names split by receiver type, which is precisely the thing Java is known for: array.length, string.length(), list.size(), three spellings of one idea and a permanent tax on the reader's memory. C# charges a smaller version of it with Length against Count. Emerald had shipped the full version without anyone noticing, because KnownByAnotherName mapped length → count and made the list case say the right thing, while the String case — the one that was actually wrong — had nothing to say at all. length is now a name Emerald does not have, and reaching for it says where it went.
And it agrees with .chars()Graphemes, not UTF-16 unitsThe same bug underneath. §3.1 promises for and .chars() can never disagree about what a character is, and they did not — but .length was value.Length, so a string those two called three characters long measured ten. Nobody had asked the third question. reverse had it too, and worse: reversing by UTF-16 unit tears an emoji into halves and reassembles it backwards, producing text that is not merely wrong but invalid. Both now go through the same grapheme enumeration .chars() does, so the promise covers every way of asking rather than the two that had a test.
And so does split("")Every character, not the whole stringThe third appearance of the same fault line, and the one that had been left undecided rather than settled. "abc".split("") returned [abc] — asked to split on nothing, it did nothing — because that is what .NET's String.Split does with an empty separator, and the built-in was a thin wrapper that inherited the host's answer without anyone choosing it. Every character is what the request plainly means, and what Ruby and JavaScript both give; Python declines the question with an error, which is defensible but declines a question that has an obvious answer. The implementation now routes an empty separator through the same grapheme walk as chars(), so s.split("") == s.chars() holds by construction rather than by two definitions agreeing — including on a family emoji, where a UTF-16 split would have returned rubble. Nothing in the corpus depended on the old behavior, which is how a wrapper's inherited answers usually go: unnoticed until someone tries the case.
No builtin propertiesarr.count(), with parensThe obvious concession was to keep count, keys and values paren-less, since they read as things a collection has. Declined, and the deciding argument is narrower than "a list is trivia": count is not one thing. On a list, a dictionary and a set it is a stored number; on a range it walks; on a string it walks, since the answer is in graphemes. So a property list would make one name a property on some receivers and a method on others — which is the split the two rows above have just been spent removing, arriving by the other door. No principle decides whether sum or keys belongs either; both compute. Zero exceptions is a rule a student can hold; a short list is trivia. The cost is s.count() where JavaScript and C# both write a property, accepted because Python writes len(s) and neither convention is the intuitive one.
A built-in method is a value tooNo exception for the standard libraryShipped as an exception and then removed, which is the interesting part. The first implementation refused word.upper as a value on the grounds that a built-in "has no declaration to bind" — wrong, and wrong in a way worth recording: Builtins.InvokeMethod takes a receiver and a name and has never needed anything else, and the built-in signatures added one revision earlier are exactly the declaration that was said not to exist. So the language had rejected the paren-less-for-?-names option for leaving a naming class unreferenceable and adding an exception to teach, and then shipped that same exception under a different name: rex.speak was a value and words.count was an error. Every comparable language allows this — Java's String::toUpperCase, C#'s method groups, Python's bound methods, Kotlin's String::uppercase — and JavaScript is the only one that allows it badly, by losing the receiver, which a bound value cannot do.
Except the ones taking a blockA rule, not a listThe single remaining gap, and it is stated rather than enumerated: list.map cannot be named on its own because what it answers is whatever the block answers, so there is no type to write down until a block is written. That is checkable at every site without knowing which methods are on any list, which is the same test the property question failed. Costs nothing anyone wants: a block is what you would pass in that position regardless. Getting here required giving the containers real parameter types, which §3.7's table had never recorded — it held return types only, so the argument checking lived scattered across the three container paths. That is now one place per container, which is where the arguments were already being checked.
What it buys, beyond callbacksThe ?. collision dissolvesUnlooked for. §3.2 records that n.even?.to_string() lexes as ?. and has to be written (n.even?).to_string() — a documented wart with a diagnostic built to explain it. With parens required the predicate ends in ), so n.even?().to_string() has nothing to disambiguate and the rule costs nothing to state. A wart removed by a change made for an unrelated reason is usually a sign the change was structural rather than cosmetic.
Accepted costempty?(), and a corpus sweepif items.empty?() is worse than if items.empty?, and that is the sharpest thing anyone gives up here — the ? suffix was chosen to read as a question and the parens interrupt it. The defence is that each mark now carries exactly one fact: ? says the answer is a Bool, () says a call happens. Roughly 45 zero-argument call sites and 30 predicates across the .em corpus changed. Paren-less arguments were never on the table and stay forbidden — print "hi" is still a syntax error — so the grammar was already unambiguous and gets no simpler; what changes is the semantics of a member read.
Why this is not Ruby's tooling trapNever was, and now not even the ergonomicsKept because the analysis holds and the conclusion moved. What defeated Ruby's tooling was foo bar baz — undecidable without semantics — not optional parens on zero-argument calls, so this language was never exposed to it and the row was right to say so. What the row got wrong was treating that as a reason to keep the feature: it established only that optional parens were safe, never that they were worth it, and Ruby's charm comes from the paren-less arguments Emerald had already refused. Taking the ergonomic half of a syntax turned out to mean taking the half that cost method references.
Member names after .Keywords permittedFound by building it: maybe.or(0) would not parse, because or is an operator keyword. The position after a dot is unambiguous, so member names live in their own namespace. JavaScript made this exact change in ES5; the alternative is an escape syntax (C#'s @class, Kotlin's backticks) that solves the same problem more awkwardly. Benefit: adding a keyword later cannot break an existing method name. Cost, accepted knowingly: x.keyword is forfeited as future special syntax, so nothing reflection-shaped can be spelled the way Java spells x.class.
Asking what a value isx is Dog, and it narrowsNever raised before, and the gap was total: with classes, traits and inheritance all shipped, there was no way to ask whether an Animal was a Dog — not deferred, not rejected, absent. Ruby answers this with .class, and would be the obvious import; it is the wrong shape here. x.class == Dog is a Bool, so the compiler learns nothing from it and x.bark() on the next line is still an error — in a language whose signature feature is flow-sensitive narrowing, that is the machinery declining to be reused. is narrows instead: past the check the name holds the narrower type, which is the same rule as if name != nothing, extended to a second question rather than added as a new one. It sits with the comparisons in the grammar and is its own node rather than a Binary, since what stands on its right is a type and not an expression.
When is is a mistakeAlways true, and never trueBoth compile without comment in C# and Java, and both are bugs often enough to name. A test that cannot fail is a warning — every Dog is a Dog — because the branch it guards is not guarding anything. A test that cannot pass is an error: two classes with nothing between them have a decidable answer, and it is no. A trait on either side is exempt from the second rule, and getting that wrong was the first bug this feature had: pet is Speaker on an Animal was refused, when a Dog below it mixes Speaker in and the test is exactly the case the feature exists for. A trait says nothing about what a subclass may later do.
Asking what a value is calledx.type_name(), a StringThe other half of Ruby's .class, split off from the first because they are different questions: this one is for reading, printing and teaching, not for control flow. It returns a String rather than a type object, which keeps a reflection API from being born by accident — §5.1 rules out runtime metaprogramming for IL2CPP, and a first-class type value is how that starts. Answered by every value including nothing, which is the case worth having, since the value that surprised you is the one you ask about. A type cannot redefine it: the name is worth having only because it means one thing everywhere, and a class that redefined it would decide what "what is this?" means on exactly the values hardest to read. The checker refuses the declaration and the interpreter answers before consulting the class, so the rule holds from both ends.
The downcast is cannot giveanimal as Dog, giving Dog?is narrows a name, which is the common case and only the common case: a field, a list element, or any expression that is not a bare variable has nowhere for the narrowing to be recorded — kennel.resident is Dog proves something the checker has no slot to write down. So the same question is also answered as a value, giving T?, and the miss then goes through ?., .or(...) and .must() rather than a second convention invented for it. One question, two answers, and knowing either spelling teaches the other. C# splits the same pair the same way. as binds tighter than the comparisons, because its answer is a value and pet as Dog == nothing is the obvious thing to write; is does not need to, since its answer is already a Bool.
It was a generic method for one afternoonpet.as<Dog>(), withdrawnRecorded because the reason it was wrong is more useful than the fix. Type arguments had just been built for interop, and with no code generator there was nothing generic to call — so the syntax would have shipped unreachable and untested, and a consumer was found inside Emerald to give it one. That is the compiler's convenience deciding a surface syntax every future reader pays for, and it was presented as diligence at the time. The line it produced was pet.as<Dog>()?.fetch().or("(not a dog)"), which is four mechanisms in one expression and reads like the TypeScript this language exists to not be. The corpus had already voted: 949 lines of games contain no downcast at all. A feature whose whole footprint is interop and the occasional field should be as quiet as the language can make it, and a keyword beside is costs nothing to learn where angle brackets cost a concept.
Which leaves angle brackets where they belongForeign calls onlyThe outcome worth keeping. With as respelled, < and > appear in a call only when the call is into .NET — AvaloniaProperty.Register<MyControl, Float>(...), where there is no non-generic form and the noise is unavoidable. They are a foreign-call sigil rather than part of Emerald's vocabulary, and a student writing games never types one. The syntax still parses, deliberately, and every use is refused with a sentence about the code generator: someone reaching for interop early should get an explanation rather than unexpected '<'.
Found by writing itA parser that span on a < bWorth recording because the shape recurs. The postfix loop was given a third way in — a < might open type arguments — and the routine it calls hands the expression straight back when the < turns out to be a comparison, consuming nothing. So the loop asked again, forever, on the most ordinary expression in the language. A branch that may consume nothing must be able to stop, and the test that catches it is not a clever one: it is a < b. The bug survived the type-argument tests because every one of them was a call that parsed.
What members() would have costTooling, not a runtime methodRuby's .methods was the other half of the request, and it is declined on a cost the other two do not carry. It needs a runtime method table; .NET has one, and reaching for it is the single biggest obstacle to IL trimming and NativeAOT — which emerald ship promises a small self-contained binary on top of. So it would spend the ship story to answer a question the compiler already knows the answer to at compile time. emerald explain <Type> and REPL completion read the same signature table the checker does, cost nothing at runtime, and work on a type you have no instance of — which .methods cannot do. Better than the thing it replaces rather than a lesser substitute, which is the only reason to decline a feature someone asked for.
Why that is .NET-safeEvery C# keyword is lowercase§3.4 emits members as PascalCase, so or → Or, if → If, class → Class — all legal C# identifiers. The collision is structurally impossible, and it falls out of a naming decision made for unrelated reasons. Caveat: VB.NET keywords are PascalCase, so a VB consumer would need [Or]. Judged marginal rather than designed around.
Array literals[1, 2, 3], indexed a[0]Homogeneous: every item must share a type, so [1, "two"] is an error. Index positions are Int. Strings are deliberately not integer-indexable (§3.2), so s[0] is a diagnostic pointing at .chars.
Division/ always gives a Float; // floorsPython 3's split, and it removes a classic trap: 7 / 2 silently gave 3 under C#/Java rules, and a student had no way to know why. Now 7 / 2 is 3.5, matching what a calculator does, and the surprising operation gets the visibly different spelling. Diverges from C# — but a student meets that trap there anyway, and meeting it with the concept already named is better than meeting it as a mystery.
// and % floor togetherToward negative infinityA matched pair, so a // b * b + a % b == a holds. C# truncates toward zero, which makes -7 % 2 come out -1 and quietly breaks n % 2 == 1 as an odd-number test. Python's rule keeps n % 2 in {0, 1}.
Exponent**, right-associativeBinds tighter than unary minus, so -2 ** 2 is -4 and 2 ** 3 ** 2 is 2 ** 9 — Python and Ruby's rules, inherited whole rather than invented. Earns its place beyond looks: Math.pow goes through doubles and can only return a Float, where 2 ** 10 gives the Int 1024. Overflow is reported, not wrapped. Not ^: every programmer reads that as XOR.
Exponent literals1e6, 1.5e-3, always a FloatNoticed as a gap in what could be written and turned out to be a gap in what was read back: "1e308".to_float() already worked, so the runtime understood the notation and only the literal syntax did not. 1e3 is 1000.0 rather than 1000, because the notation is about magnitude and this language does not pick a type from how large a value happens to be. Guarded the way the decimal point is — an e begins an exponent only when digits follow — which is the same one-character rule that keeps 1..5 from lexing as 1. and .5.
What a Float prints asSomething that could have been typedThe rule the literal was really needed for, and the bigger half. It already held for nothing, true and Suit.HEARTS, and did not hold here: display switched on whether the value happened to be whole, so 1e21 arrived as twenty-two digits while 0.0000001 arrived as 1E-07 — uppercase E, which was never Emerald syntax in any position. The language was emitting a notation it could not read. Now one form both ways, and print is a round trip.
Where the switch happensPast 253, or below 0.0001The large threshold is the only one with an argument behind it. Past 253 a Float no longer holds every whole number, so printing one as a plain integer claims a precision it does not have — 1e16 is the first round power of ten beyond that. The small end follows Python, which switches at the same place for no deeper reason than readability. Both are conventions; only one of them is a fact.
And at whatever length reads backNever a fixed number of digitsFound while fixing the above, and older than it. The whole-number branch formatted to fifteen significant digits, which is not enough for a Float: 9007199254740992.0 printed as 9007199254740990.0 — a value typed exactly, returned wrong, in a language whose entire numeric story is about not doing that quietly. The first attempt at the exponent form made the opposite mistake, asking for seventeen digits whether they meant anything, so 0.0000001 came back as 9.9999999999999995e-8: true of the double and no use to anybody. The right length is neither a floor nor a ceiling but the shortest text that reads back as the same value, which is a thing the platform can be asked for directly.
A number against a nameRejected, in the scannerFallout worth keeping. 1e is not an exponent, correctly, and it used to lex as the number 1 beside the name e — so the reader was told there is no variable named e, and offered Math.e, which mentions nothing they were trying to write. 2x, 3rd and 10px had the same shape and the same silence. A digit followed directly by a name is now refused where it is noticed, which is §3.6's point-at-the-cause rule applied to the one pass that usually gets away without it.
Float overflow stays InfinityUnlike the Int case aboveAsked deliberately once integer overflow began reporting, and answered the other way, which is worth recording because the surface inconsistency is the kind this document usually resolves. The Int case was bought because a wrap is plausible — a number that looks like an answer and is not. Infinity is not: it is visibly not a measurement, it is IEEE's own answer, every other .NET language agrees with it, and it is genuinely useful as the starting value when hunting a minimum. The two decisions differ because the failures differ, not because the rule does.
Integer overflowReported, on every operatorFound by asking what the largest Int does under each operator, and getting two different answers: ** reported overflow — the row above says so, and had said so for revisions — while +, - and * wrapped, so adding one to the largest number gave the smallest. Nothing in the document was contradicted, because the promise had been made about ** alone; the language was simply inconsistent with itself at the one place where inconsistency is invisible. The deciding argument is the shape of the failure, not its likelihood. A wrap is not a crash — it is a plausible wrong number that goes on being used, and a student cannot debug what does not announce itself. Every other rule in §3.2 is bought to convert exactly that shape into a loud one. C#, Java, Go and Kotlin all wrap; Swift traps, and Swift is the one designed after the others had shipped the consequences.
What it costsAn overflow check per operationNothing measurable in the tree-walker, and a real if small cost in the backend — add.ovf where add would do, on every integer operation in a program. Accepted knowingly, and worth revisiting only with a profile in hand rather than an intuition: the game-loop objection is the plausible one, and it is also the case where a wrong number is worst. Floats are untouched, because they overflow to infinity, which says what happened.
Keyword stylevar const func class traitRecognizable abbreviations of the words they mean. fun spells a different English word and buys a recurring question; fn is an abbreviation a student must be told about; function is eight characters on nearly every line of a class body.
Iteration keywordfor, never foreachforeach exists in C# and PHP for one reason: to be distinguishable from the C-style for (int i = 0; i < n; i++). Emerald has no C-style for, so there is nothing for a second keyword to contrast with, and adding one would be two spellings of a concept for already owns — §2.2's tax, and §3.6's "one name per thing" applied to grammar. Ruby, Python, Lua and GDScript all say for; C# is the lone exception and for a reason that does not transfer. The commitment that makes this safe: no C-style for, ever. while covers counting loops that a range cannot.
What for walksFive built-ins, no traitWritten when it was three — a range, an array and a string — and grown twice since without the row noticing, which is how a count in a heading goes stale. A set walks directly, and a dictionary walks in pairs through for (key, value) in. Still no trait, and that is still the honest gap: a user's own type cannot be walked, and the diagnostic says so rather than pretending the shape exists. A string yields graphemes, the same ones .chars gives, so walking a string and indexing its .chars can never disagree about what a character is — and §3.2 having ruled out integer indexing, walking is how you reach them at all. Before this, for took only a range: iterating an array meant .each, and iterating a string was impossible.
Iterating an array that changesThe walk is over a snapshotfor x in xs { xs.add(x) } ends rather than hanging. The program is still wrong, but a loop that terminates teaches that far better than one that appears to freeze the machine — and a beginner cannot tell a hang from a crash. C# throws instead, which is defensible but spends an exception on a case where doing the obvious thing is harmless.
break and continueUnlabelled; cannot cross a function boundaryNo labeled break: it is the escape hatch for deeply nested loops, and the honest fix for those is a function with an early return. Not addable-later in the awkward direction either — labels can be added without breaking anything (§2.5). More consequentially, neither may leave a block: items.each { x => break } is rejected, because a block is a function and Ruby's permissive version makes control flow depend on whether the enclosing call happens to yield. That error gets its own message rather than "there is no loop here", since the loop is usually visible two lines above and the compiler would look wrong.
Statement terminationNewline; no semicolon tokenNot optional semicolons — the token does not exist. Go permits them and then has gofmt strip them, which is two rules doing one job.
Line continuationTrailing operator, comma, open bracket; or next line starts . else then withThe leading-. rule is load-bearing: without it, multi-line method chaining breaks, and chaining is how §3.2 replaces the pipe operator.

TypingStatic, inferredInference is not a second discipline — it is one discipline with the annotation omitted. The var objection does not apply.
Everything is an objectUniform surface, CLR representationThe requirement is that everything responds to . and no globals operate on receivers. That is surface uniformity, achievable while Int compiles to System.Int32. Kotlin's model.
The empty valuenothingSame logic as var and constructor — a word that is its own definition. "This holds nothing" is a complete explanation. null carries fifty years of baggage and means nothing to a fifteen-year-old, nil abbreviates a Latin word, none reads as a quantity. Surfaced by drafting an error message, not by the decision tables.
NullabilityNon-nullable by default, ? to opt inOne character, compiler-enforced, and maps onto C#'s nullable reference types for interop. Avoids teaching monads.
Using a nullableFlow-sensitive narrowingAfter if p != nothing, p is a Player inside the branch. Kotlin's smart cast, TypeScript's narrowing, C#'s nullable flow analysis. Non-negotiable — without it, non-nullable types are miserable to use. Teaches well: once you have checked, the compiler knows. One limit, raised by an outside reading and then confirmed by a crash: a check proves what a variable holds at that moment, and a call in between can undo the proof. if name != nothing { clear() print(name.count()) }, where clear assigns name, compiled and produced the exact null-reference failure this section exists to abolish. What was built is narrower than this row said, and the row is corrected rather than the code. It claimed such a variable "is not narrowed at all", which is Kotlin's rule; the checker actually refuses the narrowing only where a call that could reach the variable stands between the check and the use. That is sound — nothing else can change it in between, since there is one thread and no other way in — and it accepts a great deal of ordinary code Kotlin's blunter version rejects. Worth recording as the rare correction in this direction: the implementation was better than its documentation, which is a failure of the same kind as the reverse and only looks harmless. Only captured assignments count either way: a variable a block declares for itself stays narrowable. The diagnostic says why the check does not reach, rather than repeating "check it first" to someone whose check is on the line above.
What narrowing producesThe stripped type, not "anything"The first implementation narrowed Player? to an unknown-but-not-null type. That is enough to reach .name, so the gap survived the whole nullability implementation unnoticed — it only surfaced when an operator had to find add on the narrowed value and there was no longer a type to find it on. Narrowing now produces the real Player. A reminder that "the tests pass" and "the type is right" are different claims.
Narrowing past a guardA branch that cannot fall through is an elseFound by writing tic-tac-toe. if piece == nothing { return "-" } proved nothing about the rest of the block, so a value checked on one line was still a maybe on the next. Written longhand with an else it narrowed; written as the early return it did not. That put the penalty on exactly the shape the language encourages — §3.1's one-line guard exists so a check need not indent everything after it, and it was the form that lost the narrowing. The rule is now the plain one: an if with no else whose branch ends in return, throw, break or continue makes the remainder of the block its else, so what the condition disproved is proved from there on. Conservative where it cannot tell — a branch that might fall through narrows nothing. The corpus had been written around the absence: three places carried an .or(...) below a guard that had already settled the question, including the tour's own error-handling section, and reading .or on something that is never nothing now says so rather than reporting a missing method.
Fallbacks.or(default), .must()Methods, not operators — discoverable by typing ., chainable, no cryptic sigil. ?? was rejected for the same reason as the ternary. Compiler intrinsics, since a null reference cannot dispatch, but indistinguishable from methods to the reader. .or(x) is exactly if v != nothing then v else x, so narrowing is the primitive and this is the convenience — §2.1 in miniature. Which it was not, for two revisions. Being written as a call, it was evaluated as one: here.or(fallback()) ran the fallback and threw the answer away, so a fallback that consumed an id consumed one for a value that was already there, and a fallback that could throw could kill a program that had nothing missing in it. Both halves of this row said otherwise — an intrinsic does not evaluate an argument it has no use for, and the if above it evaluates one branch — and so did every construct beside it, including the or operator it shares a name with: a or b short-circuited where a.or(b) did not, one line apart, same word. Now an intrinsic in fact. Two smaller holes closed with it, both from sitting in no signature table: count.or() read past the end of its own argument list at runtime, and count.or("none") on an Int? was accepted while handing back a String from an expression the checker was calling Int.
Why must and not valueThe dangerous thing should not have the mildest nameNon-nullable types exist to turn a runtime crash into a compile-time error, and this is the one construct that turns it back — so it is the only place in the language where a name can make a program worse. .value() read like an ordinary accessor; Kotlin spells the same escape hatch !!, deliberately ugly so it stands out in review. .must() states a claim, which is what it is, and its failure can then name the claim rather than the crash: "This is nothing, and .must() said it would not be." The old name is not an alias — §3.6 allows one name per thing — but it is in the suggestion table, so reaching for it says where the name went. The remaining half of the objection stands and is worth revisiting: a student taught that a String? has no methods still meets two that work, and .or earns that exception by being sugar over narrowing where .must is sugar over nothing. A warning when narrowing was available on the same line would answer it, and is buildable now that warnings exist.
Optional chaining?., checked one link at a timeRejected for v1 on two grounds, of which only one held. The silence objection — a beginner writes p?.name and never learns the branch did not run — is a fact about C#, where a?.b.c() poisons the rest of the chain and needs an end-of-chain rule to say so. Non-nullable types remove it: every ?. hands back a T?, so the next link needs its own ?. and the checker asks for it by name, and the chain ends at a .or(...) the reader can see. No chain can run past a missing value, so per-link short-circuiting is the end-of-chain rule. The collision objection held, and costs one sentence: a ? in a name is never immediately followed by a dot. So n.even?.to_string() reads as ?. — and requiring parentheses on every call (§3.1) removed the cost of that entirely. The correct spelling is now n.even?().to_string(), where a ) stands between the two marks and there is nothing to disambiguate; the awkward (n.even?).to_string() this row was written to justify has no reason to be written. The rule survives, since someone can still type the old shape, but it is a diagnostic rather than a shape the language forces on anyone. What actually changed the answer was building the alternative: narrowing binds names, not paths, and cannot soundly bind paths because a member may be a property, so two nullable links cost a local and a nested if each. That is verbose enough that the cheap fix is a non-nullable field holding a fake — the sentinel habit this whole section exists to break, arrived at by way of the tooling. Reads only: a?.b = 1 is refused, because a write that may not happen is an effect the statement does not state.
Where the maybe check was not happeningPrimitives, all of themA built-in method is found by head type, and a head reads through a ?: List<Int> and List<Int>? both look up as List. The container paths match on the concrete type and so noticed anyway, but the primitives were looked up by that name alone — so an Int? was looked up as an Int, every method on it passed the checker, and the program failed at runtime with the null-reference error this whole section exists to abolish. The types it hit are the ones most maybes actually have. to_int_maybe, find and a dictionary lookup nearly all hand back a primitive optional, which is to say the examples this section is taught with were the ones going unchecked. Invisible for as long as it was because the corpus was written by someone who knew the rule and wrote .or(...) anyway; it took a program written to find out what the language does, rather than to show what it does, to reach the case.
Where to stopNo .map, .and_then, .filterOnce .or() exists these are easy, and they are the road to a full Option API — precisely the complexity rejected when ? was chosen over option types. .or() and .must() earn their place by being what a beginner reaches for. Held until real demand argues otherwise.
Throwing and catchingthrow, try { } catch e { }The syntax for the row below, which had been settled for months with no way to use it. At least one catch is required — a try that swallows nothing does nothing, and one that swallows silently is worse. Said untyped in v0 for as long as it existed, and the rows below settle it the other way. The IOU named its own condition — "catching by type needs user-declared error classes first" — and that turned out to cost one prelude declaration.
Every field gets a valueDefinite assignment, checked per pathCloses the hole this document listed as open one revision ago: class Tag { var name: String } built successfully and left name holding nothing while the checker went on insisting it was a String. The central promise of non-nullable types, broken in silence, with the failure surfacing later at whatever line first called a method on it — the null-reference experience these types exist to abolish. A non-nullable field with no initializer must now be assigned on every path out of the constructor, and a class with such a field must have one. Excluded, correctly: a nullable field, for which nothing is the declared value; an initialized one, which runs before the constructor; and a struct with no constructor, whose implicit one fills everything.
Constructor chainingsuper(name), first statementThe hole an outside reading called the clearest structural one left, and it was sound rather than broken, which is why it survived so long: definite assignment refused a subclass constructor that left the base's fields empty, so nothing could crash. What it did instead was force the subclass to do the base's job — self.name = name copied down, once per subclass, with the base's whole field list copied with it. That compiled, silently skipped whatever the base's constructor did with those values (a Dog whose Animal normalized its name got the un-normalized one), and broke the day the base gained a field. A safe hole is still a hole; it had just moved the failure from a crash to a wrong answer, which is the worse of the two to debug.
Why firstPosition, not "before self is read"The permissive rule is available and provably sound — the flow analysis doing definite assignment can already prove nothing inherited is read first — and was rejected for costing a paragraph where a position costs a sentence. Reading an inherited field before the base filled it is the null-reference shape §3.2 exists to remove, arriving through the one door that analysis was not watching. What the position rule costs is computing an argument beforehand, and that work fits inside the parentheses: super(name.trim()). Java and C# land in the same place, C# more strictly still, since : base(...) is an expression with no room for a statement before it at all.
When it is requiredWhen the base needs argumentsA base constructor taking nothing is called implicitly, so a hierarchy whose base has nothing to fill never mentions it — and the base still runs, which the old behavior did not manage either. One that needs arguments must be called, because there is nothing sensible to pass on the writer's behalf. Making it always explicit was considered on the override precedent — say out loud what you are doing — and rejected: override announces something surprising, a method quietly replaced, where a base constructor running is what anyone would already assume. A keyword that states the expected teaches nothing.
What it buys backDefinite assignment stops askingThe payoff, and the reason the two changes belong in one commit. FieldsNeedingAValue walked the base chain, and had to, since nothing else was going to fill those fields. Now the base's constructor always runs, so it does not — a class answers for its own fields and no others. The check got smaller as a result of the language getting a feature, which is the direction that ought to be suspicious and in this case is just correct: the analysis was compensating for a missing construct.
One super, two usessuper(...) builds; super.name() callsFalls out of §3.2 having bound super as an ordinary name rather than a keyword. It is the class above, and the two things you can do with a class above are run its constructor and call its methods — so the value is made callable and nothing else changes. A three-level chain works because each level's super carries the class that declared the running constructor, exactly as it already did for methods, and for the same reason: taking the receiver's own class would loop.
What counts as a way outEvery return, plus the end — not throwThe half that is easy to get wrong, and wrong in the dangerous direction. An analysis that only inspects the end of the constructor accepts return unless ok? written above the assignments: the path that reaches the end did assign everything, and the path that returned early handed back an object anyway. Written that way here first, and caught by a test whose expected output was wrong-looking. throw is genuinely not an exit — it abandons the object rather than returning it, so no one ever observes those fields. Conservative everywhere else: a loop may run zero times and a try may fail partway, so neither promises anything on its own.
A valueless return with a guardreturn unless ok?; if needs one token of lookaheadDid not parse — return assumed anything following it was its value, so a modifier came out as "Expected a value, found 'unless'". unless is never an expression, so it is always the guard. if is genuinely ambiguous, since return if ready? then 1 else 0 returns an if-expression while return if done? returns nothing under a guard — told apart by whether a then appears before the line ends, which is the same test §9 already uses to separate if-statements from if-expressions.
Runtime failures are catchableNot merely avoidableA catch handles both a thrown value and the interpreter's own errors, so "banana".to_int() can be recovered from rather than only sidestepped with to_int_maybe. Deliberately does not catch exit or a return unwinding through: neither is a failure.
What an error isAn ordinary class, declared in the preludeError was a compiler intrinsic: a C# EmError holding a string, a kernel function to build one, and two hand-written signatures. Everything a class already does came free and was verified before any of it was built — inherited constructors, fields of its own, super(...), is, type_name(). The feature needed no new machinery at all, only the removal of the special case that was standing in for it. That is the same lesson §3.7 took from the shared fourteen: one behavior implemented once beats four parallel paths.
Catching by typecatch e: NotFound { }The colon is the annotation written everywhere else in the language, so there is no new punctuation and no new keyword — the grammar went from 51 productions to 52, and the keyword count did not move. The handler receives the declared class rather than the base, which is the entire reason to write the type down: e.field on a program's own error resolves. A clause with no type still catches everything and is still what a program that does not care should write.
Why this could not wait for the backendA CIL catch handler is typed by constructionThe argument that moved it ahead of §5. Clause orderSource order, and an unreachable one is reportedC#'s rule, for C#'s reason: a handler that can never run is always a mistake about which error goes first, never a deliberate choice. So a wide clause above a narrow one warns rather than failing silently at a run that never reaches it. An error matching no clause keeps travelling, which is what a try that does not handle something has to mean.
throw is checkedA String or an Error, and nothing elseFound while writing the row above, and older than the feature that exposed it: the checker called TypeOf on a thrown value and discarded the answer, so throw 42 compiled and died at run time with a message the interpreter had to invent. A statically typed language letting a type error reach the running program is the failure its type system exists to prevent, and it had been reachable in one line since throw was built.
message is a fielde.message, not e.message()Follows from the row above it: an error is a class, and the text it carries is stored rather than computed, so §3.1's rule — a value is read without parentheses, a method is called with them — picks the spelling. A breaking change, worth it because the old form was the intrinsic showing through. The evidence it was already the natural reading: §5's open questions and the formatter's own fixtures both wrote e.message, in a language where that did not compile.
No finallyDeliberate, and not a deferral of the same thingThe obvious fourth piece, and left out because it answers a question nobody has asked yet. What a program will actually want is a resource construct, and with — the word every language uses for it — already means mixing in a trait. Adding a keyword now would pre-empt that conversation with the worse of the two options. File and IO will force it honestly, and §2.5 prefers the reversible choice.
What building it brokeAn uncaught error reported a line the reader could not seeMaking Error a prelude class gave it a prelude constructor, and running one moves the interpreter's idea of the current line into a file the programmer has never opened. An uncaught throw in a seven-line program reported line 13 of that program, against its own name. Fixed by stamping the line where the throw is written rather than letting the unwinding fill it in later, and again on the rethrow path when no clause matches. Both were found by running the feature, not by reading it — the same way every real bug in this document has been found.

The only thing missing was that nothing ever called it. Not a decision anyone had made either — no row in this document mentioned the subject before this one.
The asymmetry it removesUser types were the only kind that could notEvery built-in stringifies; a class printed <Money> however carefully its author had written the method. The corpus had already askedSeven hand-written calls, and a special case a day oldThe evidence was sitting in the repository before the feature was proposed. examples/operator_traits declared func to_string(): String on Money — exactly what C# would — and then wrote #{lunch.to_string()} seven times, because interpolation did not call it. The shape is not the author's to chooseNo parameters, returns String, and the annotation is requiredStricter than the ? biconditional it is modelled on, and deliberately: that rule is about a name reading honestly, and a program ignoring it still runs. The required annotation was earned rather than assumed — an unannotated to_string handing back an Int printed <C> with nothing said, a value silently ignoring the method written to describe it, which is the invisible failure §2.6 exists to refuse. C# cannot express the method without the type either.
Enums tooMore than C# managesEnum.ToString cannot be overridden in C#, so a named constant prints its name and that is the end of it. A to_string with no endReported, not a dead processreturn "I am #{self}" calls itself forever. What it lowers toToString, with nothing addedFalls out of §3.4's naming rule rather than needing one of its own: members are emitted PascalCase, so to_string becomes ToString — which is already the virtual method every CLR type has. An Emerald class that says how it prints will therefore print that way from C#, in a debugger, and in string interpolation on the other side of the boundary, with the code generator doing nothing special. The alignment is luck rather than design, but it is the kind worth writing down before someone breaks it.
throw "oops"Shorthand for throw Error("oops")A spelling, not a second concept, so §2.2 makes it free. Throwing anything else — an Int, an instance — is an error naming both forms.

Mutabilityvar mutable, const immutableBoth words are their own definitions — a variable varies, a constant does not. let was considered and rejected: in math it declares a fact that holds, which is immutable semantics, so let-as-mutable borrows the familiarity while inverting the meaning. Writing a list typeList<String>, one type argumentThe checker could always represent it — array literals, .map, element types and the for loop all depend on it — and only the annotation grammar could not spell it. That was not an inconvenience: parameters must be annotated, so a named function or method could not take an array at all, and could not declare that it returned one. Lists lived inside a scope. It survived this long because everything built on top of them ran on inference and never needed to write one down. Nesting needs no special handling, since Emerald has no shift operators for >> to be confused with. Not the generics question — §5.3 stands, and this is consuming the one container the compiler owns, never declaring another.
Writing a callable typefunc(Int): String — the header without the nameUntil this existed only built-ins could take a block, so §2.3 rested on a claim nothing could fund: a library could not offer map, each, or a callback, and §7's GUI plan — Window("Guessing Game") { label(...) button(...) { ... } } — could not be written in Emerald at all. Raised by an outside reading of the language, and the shape was chosen against two alternatives. (Int) -> String is what Kotlin, Swift and TypeScript spell, and puts a second arrow beside the => that already separates a lambda's parameters — change: (Int) -> Int a line above items.map { n => change(n) }. Block<Int, Int> reuses the generic form List<T> already has, but which argument is the return value is a convention the syntax never shows, which is exactly the C# Action/Func split wearing one name. Reusing func adds no punctuation at all and derives from a rule already known: a function's type is its header with the name removed, and the return is left off when there is none, just as on a declaration. A block's parameters are then typed from the shape the receiving function declares — the same contextual inference that already made numbers.map { x => x * 2 } know x is an Int, now available to anything anyone writes.
And comparing oneParameters against, return withIt compared parameter count, and nothing else. So func(String): String was accepted where func(Int): Int was asked for, called with an Int, and its answer used as a String — no complaint at any stage, from a checker that had the entire shape of both written down and compared one integer. Parameters go the opposite way from the return: what is handed over must accept everything the receiver will pass it, and give back something the receiver can use. A receiver that declares no return still takes anything, because discarding a value is not a mistake and func() means the answer is not looked at.
Argument typesChecked at the callThey were not checked at all. Found while testing whether the new array annotations did anything, which they did not.
List literal inferenceThe narrowest shared typeFound by building inheritance: [rex, tweety] must infer List<Animal>, not fail because a Bird is not a Dog. "First item wins" sufficed until subclasses existed, which is why the gap stayed invisible through the whole array implementation.
self is not a keywordAn ordinary bindingA method's scope simply contains self, so self.name is plain member access. No AST node, no parser case, no special handling in the checker or interpreter — the feature costs one line at each call boundary and nothing anywhere else.
Field accessself.name requiredApplies the author's own classroom finding: students identify variables in JavaScript because let marks them and struggle in Python where nothing does. self. is that marker for state. Five characters for a distinction otherwise held in the head.
Visibility_name, compiler-enforced; one levelZero keywords, and visible at the use site rather than only the declaration. Accepted cost: changing visibility is a rename. A stricter level can be added later without breaking anything (§2.5).
Constructorconstructor; called as Dog("Rex")Frequency governs abbreviation: var and func appear on every line and are worth shortening; a constructor appears once per class, so length is nearly free and should be spent on clarity. constructor is the word students are taught for the concept — zero translation. init abbreviates jargon into more jargon; initialize is Ruby's but pairs with Dog.new, so you write one word and call another; the class name brings Java's rename hazard and a grammar special case. No new at the call site — construction is a call.
OverloadsPermitted, with defaultsType-based dispatch is what default values cannot do, so both earn their place.
RedefinitionAn error only where no argument could tell two apartTwo functions of one name previously overwrote each other in silence, so calls to the first went somewhere else with no warning — the worst possible handling. Rejected now, naming the first definition's line. The row below describes the eventual behavior; this is what happens until it exists.
Default valuesEvaluated on every call that omits the argumentNot once at declaration. Python evaluates once, which is why def f(x=[]) shares one list between every call that leaves x off — a bug famous enough to have a name, sitting somewhere a beginner has no reason to look, and unfixable without understanding when the default ran. Evaluating per call costs a tree-walk of an expression that is usually a literal, and there is nothing left to share. It also makes the default an ordinary expression rather than a restricted constant, which C# requires and Emerald does not need to.
What a default can seeParameters to its leftfunc box(width: Int, height: Int = width). Parameters bind left to right, so the ones already bound are simply in scope — this falls out rather than being built. A parameter to the right does not exist yet and is reported as an unknown name, which is accurate but generic; a message naming the ordering would be better and needs an expression walk to detect.
What overlap meansNo argument could tell the two apartNot equality of parameter types but indistinguishability: Int and Float overlap because an Int widens into a Float, and Animal and Dog overlap because a Dog is one. Checked across the arity range rather than a count, since defaults are applied first — which is what makes f(a: Int) and f(a: Int, b: Int = 0) a clash, the exact pairing C# advises against in a language that permits it.
Where defaults may appearLast, and contiguouslyOnce a parameter has a default, every parameter after it must have one. Arguments are matched by position and skipping a position is not a position, so a non-defaulted parameter behind a defaulted one could never be given a value. Rejected at the declaration rather than at each doomed call — the same principle as the overload-ambiguity row above: the error belongs to whoever created it.
Overloads, builtFunctions, methods, type-level methods, and operatorsA method name now holds every overload of it. The rule about what a subclass does to an inherited set was reversed later — see below — and this row read "replaces the base's set for that name" until then. The trait machinery was the part at risk and came through untouched, because Provides and Missing only ever asked whether a name existed. Which was the hole, not the reassurance it reads as. Asking only for the name meant abstract func label(): String was satisfied by func label(size: Int): Int — wrong arity, wrong parameters and wrong return type, accepted for traits and abstract classes alike, so a declared contract was a comment. A class's answer is now matched against the shape that was asked for. An unannotated requirement still asks for nothing in particular, which is exactly what keeps the operator traits working: the prelude declares abstract func add(other), and a type's own add takes and returns itself. One rule had to be written down that had not needed saying before: a class's own method replaces what a trait provided under that name rather than joining it, since otherwise mixing in a trait would silently overload every method written to replace one of its defaults.
What a function returnsChecked against what it saysIt was not, for the whole of v0. func name(): String { return 42 } passed, and the mistake surfaced at the call site as no method named upper on Int — an error about the caller, for a fault in the callee, which is the shape of diagnostic §3.6 is written to prevent. The machinery was all there: a stack of return types, pushed and popped around every body. Every frame pushed Any, and the stack was read only to ask whether a return was inside a function at all, so the one annotation a caller relies on was the one nothing verified. Worth recording as a fact about testing, not about types. Two hundred and fifty golden cases passed before this and after it: the corpus was correct throughout, so no test could have failed, and no amount of that suite would ever have found it. A function with no declared return type stays unconstrained, which is the existing rule and not a concession — the annotation is the promise, and where there is none there is nothing to hold anyone to.
And that it returns at allEvery way out, or none of them countsThe other half of the row above, missing for as long as it was. A body promising a value could fall off its end: func f(n: Int): Int with a lone if handed back nothing, which then bound to a variable declared Int and failed at whatever touched it next — an error about the arithmetic, for a fault in the function three lines above it. That is non-nullability defeated by the type system's own omission, which is a worse failure than the null it exists to prevent, because the value arrives wearing a type that says it cannot be there. A throw counts as a way out on the same reasoning §3.2 already uses for constructors: nobody receives the missing value, because nobody receives anything. while true with no break never falls through; a loop that might run zero times and a try that might fail partway promise nothing on their own, which is the conservative direction.
Overloaded operatorsFall out of overloaded methodsAn operator is a method (§3.2), so overloading one is overloading the other — Vec + Vec and Vec + 10.0 are two add methods and no new machinery. Unplanned, and the clearest sign the operator-as-method decision was the right shape: a feature nobody designed arrived by not being prevented.
Overridingoverride required; super reaches what it replaced§3.2 let a subclass's method replace what it inherited and said nothing about which of the two mistakes had been made. Meaning to replace and failing — func spek beside speak — compiled, and the dog never barked. Not meaning to and doing it is worse: a reset written without knowing the base had one, where the base's own run then calls the wrong version and both classes look correct in isolation. That is the fragile base class, and it is the half a reader cannot find by studying the code they wrote. A keyword rather than an attribute, because §3.8 reserves attributes for what generates no code and changes no checking, and this decides whether the program compiles — Java's @Override is advisory, which is the thing being rejected. It sits beside abstract and static, needing no new mechanism. Required only where something is replaced: implementing an abstract member replaces nothing and stays bare, while replacing a trait's default does need it, since a default is an implementation — so the rule has no exceptions on its first day.
super, not base or parentBound like self, not a keywordparent is the only one of the three a beginner reads without being told, and it loses on a fact about this project rather than about language design: self is deliberately not a keyword, so whatever this is gets bound as an ordinary name in method scope — and transform.parent is core Unity vocabulary, so a student would shadow it inside the very lessons Emerald is being built to teach. base carries moderate collision risk and explains itself only to someone who already knows the term. super collides with nothing anyone names, pairs with the extends already taken from that family, and is the one word Java, Ruby, Python, Swift, Kotlin and JavaScript all share. It carries the class that declared the running method rather than the receiver's own class, which is what stops a three-level chain looping — and without it self.speak() inside an override was not a diagnosable error but a stack overflow that killed the process.
Overload ambiguityRejected at declaration, not at the callC# resolves at the call site with subtle rules, and its own guidance is to avoid mixing optional parameters with overloads — a language advising against its own feature. Overlap is decidable here (finite arity, static types), so the error lands on whoever created it: "greet already has an overload matching this one once defaults are applied."
What a subclass does to an inherited overload setIt joins it; only the matching version is replacedA reversal. §3.2 had a subclass declaring draw() leave itself with no draw(Int) at all — C++'s hiding rule, and the odd one out among every language Emerald otherwise borrows from: C#, Java and Kotlin all leave the siblings reachable. Now an own method replaces the inherited one taking the same things and nothing else, so circle.draw(3) reaches Shape's.
Why it could not standThe rule stopped at the boundaryThe decisive argument is §5's, not §3.2's. A Circle emitted to IL inherits Draw(int) whatever Emerald says, so a C# caller sees the sibling; and if Shape.draw(Int) is virtual, a call through a Shape reference reaches it on a Circle — a method the rule said did not exist. A language rule that only holds until something crosses the boundary is not a rule, it is a local convention with a hole in it, and every workaround for the encoding (a shadow that throws, a new-style redeclaration) buys the fiction at the cost of a method that lies. §5's question 09 is answered by deleting it.
What override means nowA claim about one signatureIt had been about a name, which was consistent with hiding a whole set and is not consistent with anything else: override func draw() written below a draw(Int) stated a claim about one version while silently removing another nobody mentioned. The keyword exists precisely so that replacing something is said out loud, so it now matches parameters — and an override that matches nothing above says so.
What the change brokeThe operator traits, immediatelyMerging instead of replacing made the prelude's abstract func add(other) a sibling of a type's own add(other: Point) rather than the contract it answers, and self.x + other.x inside Point.add started reporting "Cannot use + on Int and Function". An abstract declaration is a requirement, not an overload: once a class answers the name the requirement is discharged, and carrying it in stands an unannotated contract beside a real signature as though the two were versions of one method. Caught by operators_wrong_operand, which is a test about something else entirely.
One routine checks every callFunctions, methods, statics, constructorsMethod calls were checked for neither arity nor argument types, because they resolved through a different path that had never counted anything: dog.rename("a", "b", "c") sailed past while the identical mistake on a free function did not. The two paths now share one routine, so a method's diagnostic cannot drift from a function's and cannot go missing again — the reason the gap existed was that there were two places to remember, and one of them was never written. Built-in methods stay unchecked, honestly: the signature table records what they give back, not what they take, so there is nothing to check against until it does.
PropertiesA var with a get / set bodyNot a separate feature. A var without a body is a field; with one it computes; the call site cannot tell, so promoting a field to a property never breaks callers. C#'s { get; set; } boilerplate exists only because C# keeps fields and properties distinct — collapse the distinction and the boilerplate has nothing to do.
EnumsA closed set of names; no payloads§6 said to wait for the GUI work to demand this, and it was built earlier than that on the strength of the harvested demand already recorded — alignment, dock, orientation, color, every one of them a plain name. A tagged union is a different feature wearing the same keyword, and §3.7's admission rule says start with what was asked for. The alternative being replaced is passing strings: align("center") compiles and then does nothing, which is precisely the checking the type system exists to provide.
And methods, after allPayloads were the argument, not methodsThe row above says no payloads, no methods, and everything it argues is about the first: a tagged union is a different feature wearing the same keyword. A method is not one — it is a function whose receiver happens to be an enum value — and the row beside it already said the machinery was there, since an enum is a ClassInfo with a different Kind. What the omission actually cost is visible the moment a program has an enum and a question about it. Three games produced Board.other(piece), Wordle.rank(mark) and Wordle.better?(mark, than): every fact about an enum parked on an unrelated type, each one a function operating on a receiver, which is exactly the shape §3.2's all-objects rule exists to abolish. The language was requiring the thing it forbids. Values first, then members, instance and static both. A var is refused, and so is an abstract method — an enum is closed, so nothing below it could ever supply one. Payloads stay out on their own terms.
Enum value casingSCREAMING_SNAKE, like any constantColor.RED. A value is a constant of its own type, so §3.4's existing rule covers it and there is nothing new to learn — the casing warning already knew how to say so. Swift's .red reads better in isolation and would have needed a fourth casing to justify itself.
What an enum is made ofA ClassInfo with a different KindAnnotations, Obj values, static access and argument checking all worked the moment enums were registered alongside classes, because Color.RED is a static member and Color is a type name — both mechanisms that already existed. What needed writing was only the differences: an enum cannot be constructed, its values carry a name rather than fields, and values is supplied because asking an enum for its own members is the one thing a program cannot write for itself.
No exhaustiveness checkThere is nothing to be exhaustive overEnums make the strongest case yet for case/when, which §6 deferred for want of a compelling one. An else if chain over four suits with no compiler check that all four are handled is exactly the gap a match expression closes — and unlike Ruby's === dispatch, matching on a closed set of names needs no rule anyone has to be taught. Worth revisiting the deferral now that the thing it would match on exists.
Operator overloadingVia traits, lowering to named methodsa + b calls a.add(b), with Addable as the contract — Rust's std::ops model. Answers the question Python's dunders answer, using a mechanism that already exists. Operators stay discoverable by typing . because they are ordinary methods. Overloadable set kept small: arithmetic, Equatable, Ordered, Indexable.
The operator traitsAddable/add, Subtractable/subtract, Multipliable/multiply, Dividable/divide, Equatable/equals?, Ordered/compareBuilt, and shipped as a prelude: six ordinary trait declarations written in Emerald that the compiler prepends to every program. Synthesising them in C# would have been the same amount of code and would have created a second path through trait resolution for the built-ins to hide bugs in — this way a defect in traits breaks the operators too, loudly. equals? carries the ? because §3.4 requires it of anything returning Bool; a built-in that violated the rule the moment it was enforced would be an odd thing to ship. %, ** and // stay numeric-only — "kept small" has to bite somewhere, and no one has asked what a user type's remainder means. Dividable rather than the more natural Divisible, which already means "divides evenly" to anyone who has sat in a maths class — the audience this language is aimed at. An uglier word that means one thing beats a graceful one that means two.
Indexableat required; set_at optionala[i] calls a.at(i); a[i] = v calls a.set_at(i, v). The setter is deliberately not part of the trait's requirements — present means writable, absent means read-only. That is not a new rule to learn: it is exactly how a var with a get body but no set body already behaves, so indexing borrows a distinction the language had already made. A read-only lookup table mixes in Indexable and simply stops after at. at also takes whatever it likes — the interpreter does not force an Int before dispatching, so a grid keyed by String is expressible.
Writing an array elementa[i] = v, and the compound formsDid not work at all before Indexable — the checker typed the target, discarded the result, and accepted it; the interpreter then refused with "Only a variable or a member can be assigned to." A basic operation, missing in a way no test noticed because nothing had ever tried to write one. Found while building the trait that made the same question apply to user types.
Implicit constructorStructs only, fields in declaration orderClose to mandatory rather than a convenience: a struct is immutable, so with no constructor there is no moment at which its fields could ever be given values, and the type is unusable. §4.2's own Vector3 sample assumed this and did not compile. Every stored field becomes a parameter, an initialized one included — the alternative, where an initialized field drops out of the parameter list, reads better until someone adds an initializer to an existing field and silently changes the arity of every call. When default parameter values land, a field's initializer should become that parameter's default, which resolves it additively. Classes get nothing: they are mutable, so the argument does not apply, and C# does not do it either.
One compare, four operators< > <= >= all read its signNegative, zero, positive. Four separate methods could disagree with one another — a type where a < b and a >= b are both true is a bug no reader would think to look for. Same reasoning as != always being the negation of equals? rather than separately definable.
== without EquatableIdentity, not an errorConsidered rejecting it, on the grounds that Java's ==-on-String is the classic footgun this language exists to remove. Ruled out by narrowing: x != nothing is the primitive that non-nullable types are built on, and it has to type-check for every x. So == stays total, and a type that has not said what sameness means answers the honest question instead — whether these are the same object.
String orderingBuilt in, ordinal"apple" < "banana" needs no trait. It is the one comparison a beginner reaches for that has nothing to do with arithmetic, and it failed until operator overloading landed. Ordinal rather than culture-aware, so a program sorts identically on every machine — .NET's culture-sensitive default makes "a" < "B" depend on the operating system's locale.
Type redefinitionAn error, naming the first lineTwo types of one name silently overwrote each other, exactly as two functions once did. Found by building the prelude: a program declaring trait Addable would have replaced the built-in one and broken + with a diagnostic pointing nowhere near the cause. The prelude names get their own message, since "already defined on line 4" would point into a file the programmer has never seen.
StringsSystem.String; no integer indexingBeing System.String keeps interop free. Grapheme indexing would be correct but O(n) wearing O(1)'s syntax, and for i in 0..(s.count() - 1) { s[i] } is then quietly quadratic — in a TUI library, that is the whole workload. Swift hit this and removed integer indexing rather than document the trap. Iteration yields graphemes; .chars is one visible O(n) conversion to an O(1) array; .code_units and .code_points sit underneath.
Type-level membersstatic func, static varKept despite being the one keyword here that names a storage strategy rather than a concept. shared was considered — VB.NET's choice, and it states the observable truth (one variable shared by every instance, against var name where each gets its own) — but static is what students will meet in every other language, and the transfer is worth more than the accuracy. The call site needs no help either way, since §3.4 casing already separates dog.speak() from Dog.from_shelter_id().
Why a keyword at allInference and explicit receivers both rejectedInferring from "never touches self" is decidable and a trap: adding one self. later silently converts a type method to an instance method and breaks every caller. Python's explicit self parameter marks the 95% case to leave the 5% case unmarked — the wrong trade, and its most-criticized wart. The _ trick does not transfer: private members are common and the marker is one character; type-level members are rare.
Modules and staticsNo keyword inside a module fileA file with a class line is that class's body, so func is an instance method. A file without one is a module, which has no instances — every func there is static already, so the keyword would be noise and is disallowed.
Free functionsPermitted; become static methods on the file's classNo new mechanism — §3.3 already compiles a file to a class. math_utils.em's clamp is MathUtils.clamp elsewhere, so every function declared in a module file has a home namespace. Not quite no globals, which this row claimed until a module could see itself: an entry file's declarations stay top-level and are reachable unqualified from any file in the project. The receiver is implicit, not absent, so all-objects holds.
Value semantics need no implementationImmutability makes copying unobservableConfirmed by building it. Structs are enforced immutable — only a struct's own constructor may write its fields — and copy-on-assign was never implemented, because copying an immutable value is indistinguishable from sharing it. The row below argued this in the abstract; it turns out to be an implementation strategy, not just a teaching argument. One thing it does need, found later: copying being unobservable is not the same as equality being right, and Point(1, 2) == Point(1, 2) was false — the value semantics held everywhere except at the question anyone asks first. Structs now compare field by field, by the same == throughout, so a struct inside a struct compares by value all the way down and a class inside one compares by identity. C# gives a struct exactly this for free, and a struct that defines equals? still decides for itself. A class on its own keeps identity: nothing better has been said about it, and a reference type is the place where that is the honest answer.
Containers compare by contents[1, 2] == [1, 2] is trueFound by testing features in combination rather than singly, which is where it could only have been found: equality worked, list search worked, and the two together did not. [1, 2] == [1, 2] was false, and because §3.7 promises that contains?, index_of and remove use ==, that one wrong answer spread — a list of lists could not find a list it visibly held. The same argument as the struct row above: a container is a value in the sense that matters, so two holding the same things are the same thing, and Python, Ruby, Java and Kotlin all agree. C# is the outlier here and its own users reach for SequenceEqual to get out of it.
Why that is safe hereThe hazard is already out of reachValue equality on a mutable container is normally a trap: something goes into a set or a dictionary, gets changed, and the hash no longer finds it. Emerald cannot write that program, because §3.7 restricts keys and set members to Int, Float, String and Bool — a restriction made for a different reason, which turns out to close this door too. Worth noticing as a dependency: if key types are ever widened, this row has to be revisited in the same breath.
Where order countsA list yes, a set and a dictionary no[1, 2] == [2, 1] is false and [1, 2].to_set() == [2, 1].to_set() is true, because order is part of what a list is and is not part of what a set is. The dictionary case is the one worth stating aloud: §3.7 keeps insertion order and deliberately so, but two dictionaries with the same pairs answer every question the same way, so order is a property of how one prints rather than of what it is.
has_value? asked a different questionFixed with itThe same bug one layer down, and a sharper illustration of why one rule beats several. A dictionary's has_value? went through .NET's own equality where a list's contains? went through Emerald's, so a dictionary reported it did not hold a struct that a list beside it found without trouble. One question, two answers, decided by which container was asked.
Value typesstruct, always immutableC#'s value/reference model, minus C#'s worst footgun. Value semantics are only observable under mutation, so students meet structs when they want the stack allocation and never get bitten first.

Naming fewer stays ordinary, since ignoring an argument is allowed everywhere; reduce is the one that hands over two, and a dictionary's each the other. The check already existed for a written-down func(Int): Int, so this was the built-in block methods alone — the same shape as the standard library going unchecked while the program was.
How a lambda produces a valueOne expression, or an explicit returnSurfaced by building the interpreter: items.filter { p => p.active? } must yield something, but { p => return p.active? } is unwritable. Resolved the same way if / then was — a single-expression form carries the value, so blocks never need value semantics and §3.2's explicit return survives. One principle applied twice rather than two unrelated rules. A block-bodied lambda whose value is used but which never returns is a checker error, not a silent nothing.

A block with no value-returning way out now says so in its type, which is the fix that costs nothing elsewhere: every method needing an answer gets one for free, and so does any function declaring what shape of block it wants, through the row above. Worth recording as the failure mode this document is most exposed to — not a decision that turned out wrong, but one written down and never built, which reads exactly like a decision that was.

A student reading { p => ... return x ... } assumes it returns from the block in front of them, and the language should agree. Mostly moot in practice: single-expression lambdas contain no return at all.

A module is a class with no instancesConfirmed by building itA file declaring no type becomes a type named after the file, with every member static — so math_utils.em is reached as MathUtils.clamp(...). This needed no new mechanism at all: the module story is the class story with one flag set, which is why the row below could promise "no true globals" without inventing anything.
And it can see itselfIts own members, by bare nameEvery file could already see every other file's top-level functions unqualified. The one thing a file had to qualify was its own contents: inside helper.em, a function from main.em was in scope and a function declared three lines above was not. The asymmetry ran the wrong way round, and it was inherited rather than chosen — a module is a class, a class reaches its members through its type, and nobody asked whether that suited a file. It resolves in both passes now, and only for modules: §3.2 requires self. on a field, so a bare static beside a qualified field would rebuild the split that rule removes. Anything in scope still wins, and other files still say Text.repeat. Worth noting that this row's neighbor claims no true globals, which is not quite so: an entry file's declarations are reachable unqualified from anywhere, and that is what made the asymmetry visible.
An enum is a type, not a memberWherever it is writtenThe rule above decides what a file is by asking whether it declares a type, and an enum was not counted as one. So a file holding an enum became a module, and the enum became a member of it — a member with no syntax that reaches it, which made it a declaration nothing else in the project could name. In practice an enum could be declared in the entry file and nowhere else, which is the one file a growing project moves things out of. A file may hold an enum and functions both: the enum joins the project, the functions still become the module. A file holding only enums is not a module at all, since naming one after the file would stand a class beside the enum competing for the same name. The same omission ran through emerald test from the other end — loading a test run's declarations built the classes and skipped the enums — so no test could name an enum, including one declared in the entry file where declaring it had always worked.

A student never writes an import. Java and Go require one for everything, which is ceremony in the common case; C# added implicit usings because the ceremony was not earning its keep.
External packagesimport raylib requiredA genuine dependency is worth declaring. The distinction is meaningful rather than bureaucratic: inside the project, nothing; outside it, one line.
NamespacesThe directory treePath maps straight to .NET namespace with the project as root, so Shapes.Dog is MyGame.Shapes.Dog in IL and reads correctly from C#. Nothing to keep in sync — no namespace line that can disagree with the folder containing it.
Import side effectsStructurally almost impossibleType files (class/trait/struct) have no top-level statements to run, so importing one executes nothing. Only module files can, and their top-level code runs once on first member access — a CLR static constructor, so the lowering is free and Python's import-order problems do not arise. Built, two revisions after it was written, and it had been running nowhere at all. A module file's statements were handed through as class "members", where the checker's member switch and the interpreter's class builder both skipped anything that was not a declaration: code you had written never executed, and no diagnostic said so. They are now the type's initializer, run on first access, with an untouched file still running nothing — which is the whole point of choosing first access over startup. One thing the building settled: a module's own statics are visible unqualified inside it, because that code was written as a file's body and only became a class by §3.3's own doing. How another file reaches them is the separate question this section still leaves open.
Block scopingEvery block is a scope; nothing leaksA var declared inside an if or a loop is gone afterwards. Ruby's for leaks its variable into the enclosing scope, which was noted as a defect back in §3.1 and is not inherited.
Loop variablesFresh each iterationClosures made inside a for capture 1, 2, 3 — not 3, 3, 3. The classic closure-in-a-loop bug, which JavaScript needed let to fix and C# changed foreach in version 5 to avoid. Confirmed by test, not assumed.
HoistingFunctions yes, variables noUsing a var before its declaration is an error; functions are visible anywhere in the file. Without function hoisting, mutual recursion needs forward declarations — exactly the ceremony §3.3 exists to remove. The checker and interpreter must agree on this: they briefly did not, and the result was a program the type checker accepted and the runtime rejected.
ClosuresCapture by reference(1..4).each { n => total += n } updates the outer total. The environment is shared, not copied.
ShadowingError within a function; fine across oneC#'s rule. var x inside a block when an x is already visible is almost always a student meaning to change it, so the diagnostic says exactly that rather than "already declared". Crossing a function boundary is allowed, so a local count is legal beside a module-level count, and a block parameter may shadow an outer name. An error rather than a warning: it is nearly always a bug, the fix is one word, and warnings get ignored.
Entry pointmain.em by convention; or named explicitlyemerald run finds main.em; emerald run foo.em runs that file. Zero configuration for students, scripts still work.
A file has one of two shapesOne block-free type, or only block formsCorrects a contradiction the grammar exposed: if a block-free body runs to end of file, a later class X { } is nested, not a sibling. Resolved toward the simpler rule — the body runs to EOF with no exceptions, so nested is what you get, and nested helper types are useful. A sibling type goes in its own file, which §3.3 already encourages, or the file uses block forms throughout. Two shapes but not two disciplines (§2.2): the same declaration with its body implied or written, exactly as top-level statements relate to an explicit Main.

The honest answer is that casing is the only rule with a legitimate reason to be relaxed — a foreign API's names are not the programmer's to choose, so enforcing Emerald's convention on them is enforcing something nobody can comply with. No other diagnostic has that property, which is why no other has an escape. If a second one ever earns one, that is the moment to ask whether this is a mechanism rather than an exception.

No base type exists to infer from, so every member would warn forever. Applied to the type, not per member. Named @external at first, which promised more than it delivered: it reads as "this type is defined elsewhere", inviting the expectation that it relaxes definite assignment or the predicate-? rule too, when it only ever meant casing. @mirrors states a fact about the type and lets the exemption follow from it, which also gives the boundary §3.4 wanted and could not state: further relief, if some rule ever needs it, is available exactly to types that genuinely mirror something. It is the manual form of the automatic exemption rather than a second mechanism — inheriting from a foreign type already says the same thing.

It is also the simpler build — lazy checking needs reachability analysis, on-demand resolution, and memoization, which is why Zig's compiler is more complex for it. Eager is "walk everything once." Incremental caching is a later optimization; Phase 1 checks everything every time and will be instant at student-project scale.

A session is modeled as one file that keeps growing, with each entry's tokens shifted past the lines already there, so a diagnostic numbers and quotes correctly without the prompt inventing a scheme of its own. Everything typed is re-checked each time, which is quadratic and irrelevant at tens of lines, and buys correct scoping with nothing to keep in sync. Two rules differ from a file, both because a prompt is not a program: a bare expression prints rather than being §3.1's statement that does nothing, and a name entered again replaces the earlier one — without that, a corrected function reads as an overload of the version it was meant to fix, which is exactly what happened first.

Taking a substrings.slice(from, count)§3.2 keeps strings out of the index syntax, and the reason holds: grapheme indexing is O(n) wearing O(1)'s clothes, so for i in 0..(s.count() - 1) { s[i] } would be quietly quadratic, and Swift removed integer indexing rather than document that trap. But the conclusion had been over-applied — there was no way to take a substring at all, by any spelling, and chars() then rejoining was the only route. A method promises nothing about cost, which is exactly why the same operation is honest here and dishonest as s[i]. Counted in graphemes like everything else, so slicing a family emoji returns it whole. Running off either end gives what there is rather than failing: asking for ten characters of a six-character name is the ordinary case, and a language that throws for it is one where every caller writes the bounds check by hand. The count is optional and means the rest, matching C#'s two Substring overloads.
Filling in the asymmetriesindex_of, trim_start, trim_end, insert_at, capitalizeEach admitted by the gate at four of four, and each found the same way: by noticing that one half of a pair was present. List had index_of and String did not. String had pad_left and pad_right but only a two-ended trim. List had remove_at with nothing to put a value back. capitalize enters on the other door, since casing is culture work — and it leaves the tail exactly as written, where Python and Ruby lower-case it and so turn IBM into Ibm to fix a case nobody asked about.
Curriculum, admitted as exceptionsgcd, lcm, digitsNone of the three passes the gate: each is Ruby's alone among the four reference languages, and each is writable in ordinary Emerald. They are in anyway, on the grounds that this language is taught — gcd and lcm are how fractions are taught, and digits is the first interesting thing anyone does to a number. Recorded as exceptions rather than admitted through a third door labelled "educational", which is the elastic category the gate was built to remove: anything can be argued to teach something. An exception costs one line here and stays visible; a third door costs the rule. digits gives reading order and drops the sign, because a digit sum and a palindrome check both want it that way and a minus is not a digit. And the reason to grant the exception is worth stating plainly, because it is a design value rather than a lapse: it is often the minor conveniences that decide what someone thinks of a language. Ruby is the existence proof, and it is why gcd is Ruby's alone in the first place. A gate exists to stop a category growing by argument, not to make the language grudging — so the gate stays strict and the exceptions stay cheap, which is the arrangement that keeps both.
NaN follows IEEE nowx == x is false, and that is the pointEmerald had inherited .NET's Equals, under which two NaNs are the same value and nan < 1.0 is true — a total order, which is what a sort needs and not what an operator should say. Nobody chose it; it arrived the way split("") did. C#, Java, JavaScript and Python all answer false, and a reader arriving from any of them has already been taught that a NaN equals nothing including itself. That surprise is one they can carry; its opposite is one that would cost them. sort() still uses the total order, exactly as C# does — an operator that answers no to all four questions is not something a sort can be built on. And Float.nan? stops being a convenience and becomes required: with == following IEEE there is otherwise no way to ask, which is precisely why C# ships Double.IsNaN.
Where == and membership disagreeOnce, on NaN, deliberately§3.7 promises one notion of sameness: list search uses ==. A set and a dictionary key cannot follow it here. They hash, and a hash table holding a value that is not equal to itself does not answer oddly — it loses the value, because the lookup can never match what the insert stored. So a set holds one NaN rather than two. This is the single place in the language where the two questions differ, it is the same place C# puts it, and it is for the same reason rather than by imitation. Written down here because an undocumented exception to a stated rule is worse than the exception.
What filter gives backThe container it started with; map always a listNarrowing a container should not change what it is, so a filtered set is a set and a filtered dictionary is a dictionary — which is what lets set.filter { ... }.union(other) work at all. A range is the exception and rebuilds as a list: 1..10 without its odds is not a range, and no representation Emerald has could hold one. map gives a list from every receiver, since its answers may collide or be unhashable and it is not narrowing anything — set.map { n => n % 2 } has two answers for five members, and a set would silently swallow three of them.
Pair<A, B>The fourth compiler-owned container, and the only one that is not a collectionBuilt because three separate features were waiting on the same missing type, which is when a type stops being speculative. A dictionary's find, to_list, min_by and max_by hand back an element, and a dictionary's element is a pair; zip had nowhere to put what it joined; and a dictionary could not be walked by a loop. Compiler-owned rather than declarable, which is exactly what §5.3 permits — consuming generics is mandatory, declaring them can wait — so it is spelled with the generic grammar that already exists and adds no type syntax at all. Constructed with Pair(a, b) rather than a literal: (a, b) collides with grouping and every other bracket is spoken for, while a call needs no new grammar and reads the same. A record underneath, so two pairs holding the same things are the same pair without anyone writing an equals?.
Taking one apartvar (name, score) = bestA pair is worth having only if it comes apart again, so the destructure ships with it rather than after it. The same shape in both places it is wanted — a declaration and a loop head — so learning one teaches the other. Unambiguous with one token of lookahead, since a name can never begin with (. Neither name is annotated, because the pair already knows both types and writing them would be writing them twice. It is its own statement rather than a var carrying a list of names: nearly everything a var can also be — a property with a get body, a static, an annotated field — is meaningless here, and folding it in would mean writing "not on a destructure" into a dozen checks that currently do not have to think about it.
And a dictionary became loopablefor (key, value) in scores§3.7 kept dictionaries out of for on a reason that was sound and has now expired: for k in ages cannot say whether k is a key or a pair, and guessing is worse than refusing. The two-name form says so out loud, so the objection never applied to it — there was simply no way to write it. One name over a dictionary is still refused, and the diagnostic now points at the form that works instead of sending the reader to .keys(). A documented asymmetry closed by a feature built for another reason, which is the second time this week a missing type turned out to be the cause of something filed as a design decision.
What a pair still cannot domin, max, sumKept refused on a dictionary, and now for a reason about pairs rather than about a missing type: there is no arrangement of two values of different types that says which pair is larger. min_by and max_by work, because the block supplies the ordering the pair does not have, and the diagnostic names them. A pair also has no count and cannot be walked — it holds two things of possibly different types, so both would be asking the wrong question, and there is deliberately nothing on it to invite either.
Two inherited answers, now chosenreplace and to_float_maybeBoth were doing what .NET does and neither had been decided, which is the split("") category. replace replaces every occurrence — C#'s String.Replace, against Ruby's sub/gsub and JavaScript's replace/replaceAll split. "3.5e400".to_float_maybe() gives Infinity rather than nothing, because .NET's TryParse succeeds and hands back Infinity: overflow is a representable answer there, not a parse failure. Both confirmed by running .NET rather than by recollection, and both kept. The general rule this settles: where a question is one nobody in the room has grounds to answer from first principles, the platform's convention wins, because it is the one a reader can look up.
A dictionary walks in pairsAnd a pair is not a value hereThe one place the uniformity stops, and it stops on a missing type rather than a missing decision. map, filter and any? hand the block a key beside a value — the two-parameter shape dict.each has always had, now inherited by the rest. But find, min, max, to_list and sum hand an element back, and a dictionary's element is a pair, which Emerald had no type to express. They were refused by name, with the route that did exist — ask its .keys() or .values() first — rather than answered with a shape that did not. Inventing a two-element list to stand in for a pair would have been the available shortcut and the wrong one: it types as List<Any> and loses both halves' types at the door. Resolved by building the type, four rows down; all but min, max and sum work now, and those three stay refused for a reason about pairs rather than about a gap. This row is kept because the refusal was right while it stood: naming what is missing is what made it obvious that something was.
What this deliberately does not doA user's own class cannot joinThe most valuable version of this feature is Ruby's: define each, include Enumerable, and receive fifty methods — on your type, not only on the built-ins. Emerald has the mechanism, since traits already carry default method bodies and lower to CLR interface defaults. What it does not have is the type to write the trait with: trait Iterable<T> needs a declarable type parameter, and §5.3 defers exactly that — consuming generics is mandatory, declaring them is not, and Go went a decade on that trade. The prelude's existing traits dodge it by leaving parameters unannotated and letting the implementing class declare real types, but that trick cannot rescue map, whose body lives in the trait and so has nowhere to learn the element type from. So this ships as compiler-owned uniformity, which is what §5.3 blesses, and the trait waits on declarable generics. Recorded here because the gap is a deferral with a named cause, not an oversight.
sum stopped dropping fractions[1.5, 2.5].sum() answered 0Found by defining sum once for four containers instead of once for one. The fold started at 0L and added x is long i ? i : 0L, so every Float went to the floor and a list of them summed to zero — and the checker typed the answer Int regardless, so nothing anywhere contradicted it. Whole numbers still sum to a whole number; anything with a fraction sums to a Float, and the return type now follows the element. A bug that had been sitting in the most-used collection in the language, invisible because the one type that could reveal it was the one type nobody had summed.
Searching a listcontains?, index_of, remove use ==They used .NET's idea of sameness instead, so a type that defined equals? got true from a == b and false from list.contains?(b) — the same question, asked twice, answered differently, with nothing on the page to say which was lying. A language has one ==; a search that means something else by it is broken however defensible each half looks alone. Raised as "equality needs one consistent definition" by an outside reading, and it was the collection half rather than the operator half that was wrong. Dictionaries and sets are untouched: they refuse a user type as a key outright and say why (§3.7), which is a limit rather than a disagreement.
Methods that can missfind first last min max return T?An empty array has no first element, and find may match nothing. Returning a maybe rather than throwing makes the checker insist you handle it, and .or(0) is one call. This is the clearest everyday place the nullability design pays for itself — confirmed once arrays were built.
Block parameter typesInferred from the receivernumbers.map { x => ... } on a List<Int> makes x an Int, so x.upper is a compile error rather than a runtime surprise. Contextual typing, and the reason lambda parameters need no annotation.
The long tailimport linqGroupBy, SelectMany, Aggregate, windowing, set operations. This is how §1's two audiences stop paying for each other: a fourteen-year-old sees twenty methods, a professional writes one import and has everything.
Why LINQ is not mergedExtension methods not auto-importedNot a wall against .NET — a refusal to put two overlapping APIs in one autocomplete list. Select-meaning-map beside map-meaning-map is the actual harm, and it would be worse than the len() duplication that started this whole line of thinking.
Collection namingmap filter reject find reduceNot Ruby's select/inject. Deciding argument: select means the opposite thing in LINQ — Ruby's filters, .NET's maps. Shipping that collision on .NET would be building a trap deliberately. These names are also what students meet in JavaScript, Python, Rust, and Swift. One place Ruby's vocabulary is simply weaker.
Core typesList, Dictionary, Set — all three builtOne sequence type, not C#'s T[]/List<T> split. Named Array at first, on JS and Ruby precedent — both call a growable sequence that. Renamed because it was the odd one of three: Dictionary and Set are .NET's names used with .NET's meaning, while Array was .NET's name used with its other type's meaning. For an audience reading C# tutorials alongside — a student learning Unity above all — a growable thing called Array is a trap laid by the one language it is meant to be a bridge to. Same reasoning that chose Dividable over Divisible: a word meaning one thing beats a word meaning two. It compiles to List<T>, so the name now also matches what interop will show. Dictionary rather than Map because Map the type collides with map the method — "map is a verb and a noun" is a bad thing to explain to a beginner. Length is free on type names (frequency governs abbreviation, as with constructor), and it matches .NET.
Math is a moduleMath.sqrt, not x.sqrtThe rule below deciding its own first real case. sqrt replaces no syntax — it is arithmetic, not a loop or an awkward expression — so it belongs in a module rather than on Float. Holds pi, e, sqrt, pow, min, max; round, floor, ceil and abs stay on the value, where they operate.
.chars existsGraphemes, as a List<String>§3.2 ruled out integer indexing on strings and pointed at .chars — which had never been implemented, so the diagnostic saying "use .chars" named something that did not exist. "héllo 👋".chars().count() is 7, and reversing keeps the emoji whole.
And a string has a widthpad_left, pad_right, pad_center, repeatNothing in the language could make a string a given width, so a board, a table or a menu had nowhere to start — the games wrote all four for themselves before anything else. The BCL has PadLeft, which argues for exposing rather than competing (this section's first row) — but Emerald curates its own String surface, and these were not on it. What settles it is grapheme agreement. §3.1 spends a row on count and reverse agreeing with .chars() about what a character is; that is the bug where reversing tore an emoji in half. Width has the same exposure, and left to every project the natural .NET-shaped version gets it wrong — so the bug §3.1 just finished fixing would be reintroduced by everyone who needs a column. Built in, it is right by construction. The fill character is optional, which the built-in signature table could not previously express: it could state an exact argument count and nothing else, while an ordinary function has had defaults all along.
Three questions about charactersletter?, digit?, blank?Validating a typed letter had no answer but a hand-written alphabet constant, which is wrong for every language but English. Type API rather than a sprinkle, by this section's own split: these are what String needs, not syntax being replaced. The design question is what they mean, since there is no Char type and a character is a one-character String — so they answer for the whole string, true when every character qualifies. One rule covering both things anyone writes: typed.letter?() on a single character, and entry.digit?() on a whole field before .to_int(). Tested on the first unit of each grapheme, so an accented letter is a letter and an emoji is not. blank? is deliberately the exception and is true for an empty string: it asks whether there is anything here to read at all, and answering false would make it useless for the one job it has.
Type API vs sprinklesTwo categories, not oneOperations on the value — abs, round, min, max, to_string — are not sprinkles; they are what Int needs the way String needs length. Sprinkles are a separate, governed category. Conflating them is what made the earlier rule feel elastic.
The sprinkle testReplaces syntax, not a function5.times replaces a for loop; n.even? replaces n % 2 == 0; n.clamp(1,10) replaces nested min/max; n.between?(1,20) replaces n >= 1 and n <= 20. Each removes syntax a beginner finds hard. n.factorial replaces nothing syntactic — it is arithmetic, and belongs in Math. A decidable line where "reads aloud" was a vibe.
The Type API gateUnwritable, or table stakes — and say whichThe row above split Type API from sprinkles and then gave only the sprinkle half a test. What the type needs is not a test; it is an assertion, and anything can be argued to be what String needs — letter? was admitted on exactly that argument, correctly, but not through any gate a disagreeing reader could apply. An entry now passes one of two doors and records which. One: it cannot be written correctly in Emerald. It needs Unicode tables, culture rules, grapheme segmentation, or platform parsing, and a student who wrote it by hand would get it subtly wrong — which is precisely the letter? argument, that a hand-written alphabet constant is wrong for every language but English. Two: it is table stakes, present in a majority of Python, Ruby, C# and JavaScript — evidence rather than taste, and what §3.7 already claimed to admit on. Failing both, it is a sprinkle and must pass that test instead, or it does not go in. Two doors is weaker than one and honest about why: letter? and starts_with? both belong, for reasons that are not the same reason.
What the gate says about what shipped25 confirmed, pad_center an exceptionA test that ratifies everything already there is not a test, so it was run against String's twenty-six. Twenty-five pass. pad_center fails both doors: Python and Ruby have it, C# and JavaScript do not, so it misses the majority; and it is four lines of ordinary Emerald, so it is not unwritable. It stays as an exception granted, not as a pass — a beginner centering a banner should not have to compute margins, and the games corpus used it immediately. Recording it as an exception is the whole point: it went in beside pad_left and pad_right because symmetry felt right, which is the reasoning the gate exists to catch, and the answer happened to be yes anyway. reverse looked marginal on prior art — Ruby alone of the four — and passes on the first door instead, since reversing graphemes is not something a student can write.
One conversion, three spellingsA named pattern, so it costs one decisionSix of String's twenty-six members are two conversions wearing three forms each: to_int throws, to_int_or(0) falls back, to_int_maybe gives Int?, and the same three for Float. Counted as six independent admissions this looks like sprawl; it is one design being consistent, and the count overstates the surface by a quarter. Naming it as a pattern makes adding a conversion a single decision about whether the conversion belongs, rather than three arguments about spellings that are already settled — and it fixes the shape in advance for the ones that will come, to_bool among them. The pattern passes the gate on the first door: parsing is platform work. Each conversion then still has to earn its own place.
What the count actually says26 to 13 is the restrained ratioRaised as an alarm and worth deflating, because the alarm was aimed at the wrong number. String carries twice what Int does; Python's str carries roughly four times its int, and C#'s String about three. Strings genuinely have more to ask them, in every language, and 2:1 is the most restrained ratio in the room. The problem the gate solves was never the size — it was that the category had no rule, so it could grow by argument. A governed category is allowed to be large.
Sprinkle scopePrimitives and Range onlyNever on collections, which already carry the core twenty plus LINQ and are what students touch constantly. Ruby's Enumerable sprawl happened on the collection, not on Integer — fencing sprinkles away from the place they would do damage costs nothing.
TerminologyHouse word: sprinklesEmerald's term for syntactic sugar, and it usefully covers more than the stdlib methods below. print(x) if cond, trailing lambdas, and if / then are the same kind of thing as 5.times — optional expressiveness over a core that does not need them, governed by the same test. "Desugars" is replaced by "lowers," which is the more precise verb anyway.
AdmissionStart small, migrate as neededSeeded from what is already justified — times, upto, downto, even?, odd?, zero?, positive?, negative?, clamp, between? — and grown freely while pre-1.0, since a rule that strangles early exploration is a bad rule. The evidence gate (a sprinkle must have appeared repeatedly as a hand-written workaround) applies at 1.0, when removal stops being free.
Why they exist at allA dividend of all-objects5.times requires Int to have methods. §3.2's uniform surface was chosen for consistency and discoverability; the Ruby joy is downstream of it rather than in tension with it.
Conversionsto_int(), to_int_or(0), to_int_maybe()Throws, defaults, or returns Int?. .NET's TryParse pattern without the out parameter — the design thinking taken, expressed with a better mechanism. Named _maybe rather than to_int?() because §3.4's predicate rule is absolute: ? means Bool. The enforced rule caught the collision at design time.

Traits carry implementation and state requirements; classes inherit one base and mix in any number of traits. An interface is not a separate feature — it is a trait that implements nothing.

      if score > 90 {
          print("high")
      }

Mixing the two if forms is the error a student will actually hit. The grammar could have forbidden it with an extra rule; a diagnostic is cheaper and teaches more. That is the pattern for syntax corners here — add a message, not a restriction.

§ 5Platform constraints

Targeting CIL buys generics, exceptions, garbage collection, and the entire BCL. It also imposes requirements that are not negotiable, and are cheaper to design around now than to discover later.

5.1The runtime must be AOT-friendly

Most Unity build targets convert IL to C++ ahead of time via IL2CPP, which forbids runtime code generation. Emerald's runtime must therefore be fully static — no Reflection.Emit, no runtime dynamism. This costs nothing, because §3.2 already renounced runtime metaprogramming, but it converts a preference into a hard requirement.

5.2Subclassing .NET types is the litmus test

An Emerald class must be able to inherit a C# class and override its virtual methods with correct IL, such that the C# side calls back into Emerald. extends Behavior is exactly this. It is the single most important interop capability, and the right first target once a CIL backend exists — if it works, most of the roadmap is reachable.

5.3Generics: consuming is mandatory, declaring is not

Touching .NET at all means calling List<T>, Dictionary<K,V>, and Task<T>. Letting users declare generic types can be deferred for years — Go managed a decade by reserving generics for the compiler. The CLR reifies generics rather than erasing them, so the implementation is inherited from the platform rather than built.

"Generics" is three capabilities, and separating them settles most of the argument. Using a closed generic type — List<Int>, Task<String>, IEnumerable<Card> — Emerald has. Calling a generic method with concrete type arguments — GetComponent<Rigidbody>() — Emerald now has. Declaring a type parameter of your own — class Stack<T>, trait Iterable<T> — stays deferred, and is the only one of the three the Go argument and the C# readability complaint are actually about.

The second is required for interop, and the requirement is not a judgment call. Avalonia's AvaloniaProperty.Register<MyControl, double>(nameof(CornerRadius), defaultValue: 0.0) has no non-generic form — a custom control cannot be written without calling a generic method. Unity is softer, since GetComponent(Type) and GetComponent(string) exist beside GetComponent<T>(), but both hand back a bare Component that every call site must then cast, and Unity's own documentation says they are "not as efficient as the Generic version." Both checked against the shipped documentation rather than recalled.

And the second capability cannot cause the readability problem the third does. The type arguments at those call sites are concrete names, read left to right; there is no T to chase up through three layers, because nothing declared one. It is a cast that happens to be spelled in angle brackets. A third observation falls out of the same split: implementing a closed generic interface — class Deck with IEnumerable<Card> — declares nothing generic either, so Emerald classes can satisfy .NET interfaces on the first capability alone, which is most of what interop means.

5.4Unity integration — verified feasible

Unity compiles C# in Assets/ with its own toolchain, so Emerald cannot be a script language there. The path is precompiled assemblies, and it is documented rather than folklore: a managed DLL dropped into Assets gets a foldout in the Project window revealing its classes, and MonoBehaviour subclasses can be dragged onto GameObjects exactly like ordinary scripts. Compiling against the Unity API means referencing Unity's own DLLs from the editor install. Target framework is .NET Standard 2.1 for Unity 6 today — but see the CoreCLR note below, which supersedes this. Documented gotcha: a .dll sharing a filename with an .asmdef hides its MonoBehaviours from Add Component.

IL2CPP's restrictions land exactly where §5.1 predicted. System.Reflection.Emit is deliberately unimplemented; also unsupported are dynamic, runtime generic construction via Activator.CreateInstance with MakeGenericType, generic virtual functions not inferable at compile time, and code reachable only through reflection, which stripping may remove.

The nuance that matters: merely referencing Reflection.Emit fails the build, used or not. That splits the architecture cleanly — the compiler may use it freely, since it runs at build time and is never shipped (Mono.Cecil is the better choice anyway and sidesteps the question); the runtime library inside the DLL must not reference it at all.

The design had already paid for this

No runtime metaprogramming, compile-time expansion only, static dispatch, traits lowering to interface default methods rather than runtime-constructed generics — every one of those was chosen for tooling or teachability, and every one is what IL2CPP requires. Nothing was spent on Unity compatibility that had not already been spent.

And IL2CPP is a shipping concern, not a teaching one. Desktop builds can use a JIT backend when the restricted features are needed; IL2CPP is required for iOS, WebGL, and consoles. A classroom building Windows executables is unconstrained by any of the above.

CoreCLR changes the target, not the blocker. Unity is replacing the scripting runtime through 2026 — 6.7 LTS ships an experimental CoreCLR desktop player, 6.8 drops Mono entirely, bringing the .NET 10 BCL and C# 14. This does not affect the compilation pipeline, so the precompiled-assembly path remains the path. But it means the JIT escape hatch above will be CoreCLR rather than Mono — more capable, since Reflection.Emit works under a JIT runtime.

It also settles the target framework question. Emerald will not have a CIL backend for years, and CoreCLR becomes Unity's foundation in 6.8, so the timelines align: design for modern .NET and skip netstandard2.1 rather than carrying compatibility baggage for a world that is ending. One to watch, not to plan on: the migration moves assembly loading to AssemblyLoadContext, the mechanism behind unloading and hot reload in modern .NET. If that reaches plugin assemblies, the reload problem below softens considerably.

What remains is ergonomics, not capability. No hot reload — rebuild the DLL and wait for Unity's reimport, which is still a real regression from edit-save-play and the biggest classroom risk. No editor integration: no "Create > Emerald Script", no double-click-to-open. And debugging requires portable PDB emission so breakpoints map to .em files — well-documented but real work, without which stack traces point at IL and debugging is effectively unavailable.

Godot 4 supports .NET and likely makes the assembly path smoother still. The objection to Godot is conceptual — nodes versus GameObjects — and a wrapper is exactly what resolves a conceptual objection. The door remains open.

§ 7Implementation roadmap

Sequenced so that each phase produces something usable, and so that the parts most likely to be invalidated by external constraints come last.

Phase 0

Learn the craft

Work through Crafting Interpreters. The front half — scanning, parsing, AST, resolution — is identical regardless of backend, and transfers completely. The back half teaches stack-based bytecode execution, which is what CIL is.

Outcome — vocabulary and a working mental model

Phase 1

Tree-walking interpreter in C#

Runs real Emerald programs within weeks rather than years. This phase is where the language's semantics actually get decided — designing IL emission before knowing the semantics is the classic way to stall.

Outcome — a running language, and a REPL almost for free

Phase 2

CIL backend

Swap the backend once the language is known. First milestone is §5.2 — an Emerald class subclassing a C# class correctly. Mono.Cecil is preferable to Reflection.Emit: it writes assemblies to disk and keeps the shipped runtime clear of a namespace IL2CPP rejects on sight (§5.4). Target modern .NET, not netstandard2.1 — Unity's CoreCLR migration lands well before this phase does. Portable PDB emission belongs here too, or debugging never works.

Outcome — real assemblies, real .NET interop, working breakpoints

Phase 3

Tooling

Formatter first — it is the smallest piece and the one §2.4 depends on most. Then the LSP, which the no-runtime-metaprogramming decision makes tractable.

Outcome — emerald fmt, then editor support

Phase 4

Libraries

A Spectre.Console-flavoured TUI library first: pure managed code, no native interop, and writable in Emerald — which makes it a dogfooding test, not just a demo. Then a small 2D framework over Raylib or MonoGame, which stays entirely under the author's control. Unity after that, because it is the only part someone else's toolchain can invalidate.

Then a GUI wrapper — a Tkinter or PySimpleGUI analogue rather than a WinUI or WPF replacement. Over Avalonia: cross-platform, already admired, and — the practical reason — it runs on Linux, which matters while the WSL workaround stands. Not WinForms, which is genuinely the closest thing .NET has to Tkinter but is Windows-only and a dead end.

Two things to steal, one to avoid. Take PySimpleGUI's polled event loop — while window.open? { var event = window.next_event() ... } is a while loop, which a student already understands, where Tkinter's callbacks demand event-driven thinking. Take block-based layout, which trailing lambdas already provide with no new syntax. Avoid rebuilding a widget toolkit; wrap one.

Why this order, beyond difficulty

The TUI is a rehearsal for the GUI: the same problems — layout, widgets, an event loop, a declarative block API — at a fraction of the surface and with no toolkit to learn. Whatever it teaches about making blocks read well transfers directly.

And a GUI is arguably the strongest test of §2.3 available. Nested layout is the classic DSL case; if Window("Guessing Game") { label(...) button(...) { ... } } reads well, the claim that libraries can feel like language stops being a promise. The TUI proves it in one dimension, a GUI in two.

Known collision: a Windows GUI launched from WSL needs WSLg or an X server. Avalonia-on-Linux works under WSLg, but this is another reason to resolve the Smart App Control block properly rather than routing around it indefinitely (§5.4).

Outcome — TUI → 2D framework → engine wrapper → GUI

§ 8Learning path

The project's stated second purpose is to become a better programmer. That makes some inefficient choices correct.

Build the interpreter by hand. It is the phase that teaches the most per hour, and skipping it to reach a "real" compiler faster would forfeit the point of the exercise.

Compile-time metaprogramming deserves study time now. §2.3 makes it load-bearing rather than optional. Rust's macro system and C#'s source generators are the two nearest reference implementations, and it is the least-specified part of the design.

Learn to read IL before writing it. Inspecting what the C# compiler emits for a class, a property, and a virtual override is the fastest route into Phase 2 — and it is reading, not building, so it can start any time.

On scope

Every phase before 4 produces something that works and teaches something durable. If the project stops after Phase 1, the outcome is a working language, a REPL, and a genuine understanding of how languages are built. That is a good outcome, not a failed one — worth writing down before the ambition of Phase 4 makes it feel otherwise.

The artifact between a decision list and a parser. Writing it was how three conflicts surfaced — the modifier-if line rule, the trailing-lambda ambiguity in conditions, and the block-free class contradiction. All three are now settled in §3 and reflected below.

block_free_file = type_header NEWLINE { member }
block_file      = { { attribute } declaration }
declaration     = type_block | enum_decl | member | statement

type_header     = ( "class" | "trait" | "struct" ) Ident
                  [ "extends" Type ] [ "with" Type { "," Type } ]
type_block      = type_header "{" { { attribute } member } "}"

                  { { attribute } func_decl } "}"
member          = func_decl | var_decl | const_decl | ctor_decl | type_block
func_decl       = [ "static" ] [ "abstract" | "override" ] "func" method_name
                  "(" [ params ] ")" [ ":" Type ] [ block ]

                                    | two_names "=" expr )
property_body   = "{" [ "get" block ] [ "set" block ] "}"
const_decl      = [ "static" ] "const" ( Ident [ ":" Type ] | two_names ) "=" expr

                | if_stmt | unless_stmt | while_stmt
                | for_stmt | try_stmt

                | "break" | "continue"
                | assignment | expr

                  { "else" "if" cond block } [ "else" block ]

                       | "is" Type )

9.1What the three annotations carry

statement = simple_stmt [ ( "if" | "unless" ) cond ], same line only. A newline before if starts a new statement, because if is not among the tokens that continue one (§3.1). Without this, a following if is ambiguous between a modifier and a fresh statement.

cond forbids a bare trailing lambda. Otherwise if x { ... } could attach the block to x as a trailing lambda rather than opening the if-statement's body. Kotlin resolves this identically.

A number is digits [ "." digits ] [ ("e"|"E") [ "+"|"-" ] digits ], and every optional part is guarded by one character of lookahead. The . is a decimal point only when a digit follows, which is what stops 1..5 lexing as 1. and .5; the e begins an exponent only when digits follow, so a name that starts with one is left alone. An exponent makes the literal a Float whatever it does, so 1e3 is 1000.0. A digit followed directly by a name — 1e, 2x — is refused here rather than left to lex as two tokens and confuse something downstream.

literal covers an interpolated string, which is why it is a terminal here and a tree everywhere else. "#{a} and #{b}" scans as one token and the parser splits it, so interpolation costs the grammar nothing and the scanner one rule — a #{ that is not escaped opens a hole, and the hole holds any expr. The split happening in the parser rather than the scanner is what made \#{ hard to escape correctly (§3.1).

self and super are Ident, not keywords. Neither appears in this grammar because neither needs to: they are ordinary bindings the checker and interpreter put in scope, which is what lets super.describe() and self.name parse as plain postfix with no rule of their own (§3.2). A reader looking for them here is looking in the right place and will not find them, which is the point.

block is never a statement. With no anonymous scopes, a { after an expression is unambiguously a trailing lambda.

assignment is a statement, not an expression. It cannot appear inside cond, so if x = 5 { } fails to parse rather than silently assigning — the C-family =-for-== bug removed structurally rather than warned about. The left side is postfix, which covers x, self.name, dog.score, and list[0]. It also covers a?.b, which the grammar permits and the checker refuses (§3.2) — a rule about meaning rather than shape, so it is stated where the reason can be given.

"?." is one token, and it is why a ? in a name is never followed by a dot. The scanner folds a trailing ? into an identifier — that is what makes String? and empty? both work — but stops folding when a . comes next. One rule, no lookahead past the next character, and no dependence on types. It used to cost a shape — n.even?.to_string() had to be written (n.even?).to_string() — and costs none now that every call carries parentheses (§3.1): n.even?().to_string() never puts the two marks together.

Note also that if_stmt and if_expr are distinguished only by what follows the condition — { or then. A recursive-descent parser reads the condition, then peeks. No lookahead beyond one token past the condition is required.
