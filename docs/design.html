§ 1Position

Emerald exists because two languages the author admires each solve half the problem. Ruby is expressive but resists tooling. C# is robust but greets a fourteen-year-old with public static void main.

Emerald is a statically typed, object-oriented language compiling to CIL. It has two audiences that most languages treat as mutually exclusive:

A student's first language. Line 1 of a file is real code. Every character on screen day one can be honestly explained day one. No ceremony deferred to a later unit, no "ignore this for now."

A working language. Full access to .NET, real tooling, real performance, and the ability to build libraries and wrap engines — not a toy that students outgrow in a semester.

The bet holding these together is that the ceremony most languages impose is not load-bearing. C#'s boilerplate is not what makes C# powerful, and removing it costs nothing but familiarity.

There is a sharper way to state the goal, which took most of the design conversation to surface. Ruby's celebrated expressiveness was, in large part, DSL-ability — has_many :comments and validates :email, presence: true read like language features because Ruby let libraries behave like language. Rails did not feel like a framework; it felt like a dialect. That is the thing worth taking, and it is also precisely what Ruby paid for with runtime metaprogramming, and therefore with its tooling. Same feature, both sides of the ledger.

So Emerald is Python's small regular surface, plus Ruby's library-as-language, minus the runtime magic that made the second one expensive. Which reframes the compile-time-only constraint (§2.3): it is not a compromise accepted for tooling's sake, it is the enabling condition. A macro expands into real declarations the compiler and the LSP can see — jump-to-definition works, autocomplete works, the expansion can be inspected. method_missing offers none of that; it is a promise that something might exist. That difference is what makes a DSL-friendly language buildable rather than merely dynamic.

Origin of the idea

The immediate motivation is teaching game development. Unity's engine model is the one the author finds clearest to teach; Unity's C# API is the part that gets in the way. GDScript reads better not because it is a better-designed language, but because it is fused with its engine. Emerald's thesis is that this fusion is achievable as a library plus compile-time metaprogramming — not as a bespoke engine language.

§ 2Principles

Six rules derived during design. Each one settles a class of future arguments, which is the only reason to write principles down.

2.1

Small core, generous library

The grammar fits on two pages; the standard library does not. Ruby's upto and each are library methods, not syntax — Ruby's grammar was never the large part. This is how Lua's learnability and Ruby's expressiveness stop fighting each other.

2.2

A new spelling is free; a new concept is a tax

Two ways to write a statement with identical semantics costs a student thirty seconds. Two ways to introduce a variable with different rules costs them a mental model. unless is welcome. C#'s var-alongside-int is not.

The sharper test, arrived at when this principle had to explain its own past decisions: can a student derive it from what they already know? unless is if not — one sentence and they have it, and it desugars away before the checker ever sees it. Ruby's case/when is not derivable: when 5 matches by value, when Integer by class, when 1..10 by containment, three behaviours from identical-looking syntax. That is a rule you must be taught. ** passes because the concept comes from maths class; // passes because it paid for itself, letting / stop lying about 7 / 2.

2.3

Domain feel comes from macros, not from grammar

@export is not a keyword — it is a compile-time macro lowering to a .NET attribute. Domain-specific expressiveness is bought in libraries, so the core language never grows to pay for it. This is the load-bearing feature of the design.

2.4

There is always a blessed default

One formatter with no configuration. One build tool, test runner, and package manager, in the box. Alternatives may exist; they are not equal. The complaint about the Node ecosystem is not complexity — it is the absence of a default.

2.5

Prefer the reversible choice

Where a decision is close, start on the side that can be changed later. Adding an implicit lambda parameter later is backward compatible; removing one is not. Reversibility breaks ties that reasoning cannot.

2.6

Warnings are pedagogy

The compiler is the most patient teacher in the room. Diagnostics should name the practice, not just the fault — and point at the line where the mistake was made rather than where it surfaced.

§ 3Settled decisions

Decided during design conversation. Reasoning is compressed to the deciding argument — the thing that would have to change for the decision to change.

3.1Lexical and syntactic

DecisionFormDeciding argument
Block delimitersBracesWhitespace sensitivity forbids inline blocks, which the entire library-not-grammar thesis depends on. Python has no multi-statement lambda for exactly this reason.
Brace styleStroustrupAn opening brace ends its line, a closing brace begins one, and else is never cuddled. One invariant covering statements and lambdas alike — which Allman could not manage, since a newline before an expression-position { is ambiguous. Isolates } else {, the line where the novice confusion actually lives.
Comment syntax# line, ## doc, #[ … ]# blockForms are distinguished by the character following the hash, never by counting hashes. Because doc content is markdown, a student typing ### TODO out of markdown habit must not silently open a block that swallows code to end of file. Beats Ruby's =begin/=end, which is unused because it is ugly.
Doc comment contentMarkdown, with @ tags for the non-inferableNot a second syntax — this is what goes inside ##. Javadoc's @param duplicates the signature and goes stale. Types come from the compiler; tags carry only what it cannot know.
Attributes@name sigilReads better than [Brackets], and gives macros one surface. @ uniformly means "metadata about the thing attached."
String interpolation"#{expr}", no prefixA required prefix fails silently when forgotten — the student sees literal braces and cannot tell why.
Boolean operatorsnot and or onlyRuby's and and && have different precedence, a famous footgun. One set makes the bug unrepresentable.
Ranges1..5, inclusiveReads aloud correctly; pairs with the iterator protocol.
unless and untilNegated twins, desugared in the parserunless becomes if not, until becomes while not, so nothing downstream learns they exist. Expression-level choice, free by §2.2, and both read better than the negation they replace — until countdown.zero? over while not countdown.zero?.
unless takes no elseAn error, with the fix suggestedRuby permits it and every style guide bans it: "unless x … else …" is a double negative nobody parses correctly first time. Also warns on unless not x.
Modifiers guard, they do not loopstmt unless cond yes; stmt until cond noRuby's x += 1 until done makes a trailing modifier iterate, which is a different kind of thing from a guard and does not read as control flow. A statable line rather than an arbitrary omission.
Modifier formsprint(x) if cond, same line onlyExpression-level choice — free by §2.2. The same-line rule was implicit in the continuation rules (if is not among the tokens that continue a statement) and is now explicit, because otherwise a following if on its own line is ambiguous between a modifier and a new statement.
No trailing lambda in conditionsParentheses requiredSurfaced by writing the grammar (§9). if x { ... } is genuinely ambiguous — expr { ... } is the trailing-lambda form, so the block could attach to x. Kotlin hits this exactly and resolves it the same way: if (items.any? { p => p.valid? }) { ... }. Applies to if and while conditions and the for iterable.
Assignment is a statementNever an expressionSo if x = 5 { } is a syntax error rather than a silent bug — the classic C-family disaster where = is typed for == inside a condition, assigns, and evaluates truthy. Eliminated structurally instead of by a warning. Costs only while (line = read())-style idioms, which are unwanted here anyway.
Compound assignment+= -= *= /=Passes the §3.7 sprinkle test: removes a repetition where the variable name otherwise appears twice, which is a real source of typos. Lowers through the operator traits — x += y becomes x = x.add(y).
No ++ or --RejectedThe pre- versus post-increment distinction exists for reasons no beginner needs, generates exam questions that test nothing useful, and makes expressions like i++ + ++i possible. count += 1 is one character longer and has no subtleties. Ruby made the same call and nobody misses them.
No bare blocks{ } is never a statementEmerald has no need for anonymous scopes, and forbidding them means a { following an expression is always a trailing lambda. Previously undecided; the grammar forced it.
Three if forms parse cleanlyParse the condition, then peek{ means statement, then means expression. No grammar rule needed for the corner cases — if cond then x without an else is the error a student will actually hit, and it is answered with a diagnostic (§4.4) rather than a restriction. The pattern for syntax corners in a teaching language: add a message, not a rule.
Conditional expressionif cond then a else b; no ternaryMaking if an expression yields a smaller language: the alternative is a statement if plus ?:, which is two constructs where this is one. Ruby precedent — if x then y else z end is valid there, and its ternary is the C inheritance sitting awkwardly beside it.
Why then, not bracesBlocks never carry valuesRust's brace form requires blocks to yield their last expression, which is implicit return — rejected in §3.2. then buys the feature without touching block semantics, and its single-expression limit is a teachable boundary: multi-statement branches use the statement form. Also closes the newline-before-else wrinkle, since { versus then tells the parser which form it is in.
ParenthesesRequired for arguments, optional withoutThe caller's whole rule: if it needs information, put it in parens. Decidable at every call site with no knowledge of the implementation, so a student cannot get it wrong — s.upper and s.upper() are the same call. A mechanical property/method split was drafted and rejected: it is decidable by the method's author, not its caller, and arr.sort (new array, or sorted in place?) cannot be resolved from the call site at all.
Bare names too, in statement positionexit means exit()Found by the user: the optional-parens rule had been implemented for member access only, so s.upper called but exit silently evaluated a function and discarded it. The rule as written — if it needs information, put it in parens — draws no line between members and bare names, so the implementation was wrong rather than the rule. Restricted to statement position: there, naming a function and dropping it can never be intended, while in expression position a bare name may be a genuine value. Class names are excluded, so Dog does not silently construct one.
Statements that do nothingAn errorThe other half of the same bug, and the more valuable half: exit did nothing and said nothing. A statement that computes a value and throws it away is nearly always a typo, so total or a + b alone is now rejected. This is the "unused expression" lint that §3.1 listed as a cost of optional parens — it needed the checker rather than the parser, which is why it could only arrive now.
What this does to propertiesDissolves the call-site distinctionStrengthens §3.2 rather than weakening it. A field, a computed property, and a zero-argument method become interchangeable at the call site, so promoting one to another never breaks callers. Properties remain a declaration-side feature — a var that computes — which is where they were always useful.
Why this is not Ruby's tooling trapParen-less arguments stay forbiddenWhat defeated Ruby's tooling was foo bar baz — undecidable without semantics — not optional parens on zero-argument calls. print "hi" is a syntax error here; arguments always take parens, so the grammar stays unambiguous. Emerald takes the ergonomic half of Ruby's syntax and leaves the unanalysable half. Highlighting is easier than C#'s, which looks ahead for ( to colour calls differently; here everything after a dot is one thing.
Accepted costSide effects are invisiblearr.clear gives no visual signal that anything changed. Mitigated by library design — keep zero-argument mutators rare and imperative-sounding — not by a language rule. Also means an "unused expression" lint needs semantics rather than syntax.
Member names after .Keywords permittedFound by building it: maybe.or(0) would not parse, because or is an operator keyword. The position after a dot is unambiguous, so member names live in their own namespace. JavaScript made this exact change in ES5; the alternative is an escape syntax (C#'s @class, Kotlin's backticks) that solves the same problem more awkwardly. Benefit: adding a keyword later cannot break an existing method name. Cost, accepted knowingly: x.keyword is forfeited as future special syntax, so nothing reflection-shaped can be spelled the way Java spells x.class.
Why that is .NET-safeEvery C# keyword is lowercase§3.4 emits members as PascalCase, so or → Or, if → If, class → Class — all legal C# identifiers. The collision is structurally impossible, and it falls out of a naming decision made for unrelated reasons. Caveat: VB.NET keywords are PascalCase, so a VB consumer would need [Or]. Judged marginal rather than designed around.
Array literals[1, 2, 3], indexed a[0]Homogeneous: every item must share a type, so [1, "two"] is an error. Index positions are Int. Strings are deliberately not integer-indexable (§3.2), so s[0] is a diagnostic pointing at .chars.
Division/ always gives a Float; // floorsPython 3's split, and it removes a classic trap: 7 / 2 silently gave 3 under C#/Java rules, and a student had no way to know why. Now 7 / 2 is 3.5, matching what a calculator does, and the surprising operation gets the visibly different spelling. Diverges from C# — but a student meets that trap there anyway, and meeting it with the concept already named is better than meeting it as a mystery.
// and % floor togetherToward negative infinityA matched pair, so a // b * b + a % b == a holds. C# truncates toward zero, which makes -7 % 2 come out -1 and quietly breaks n % 2 == 1 as an odd-number test. Python's rule keeps n % 2 in {0, 1}.
Exponent**, right-associativeBinds tighter than unary minus, so -2 ** 2 is -4 and 2 ** 3 ** 2 is 2 ** 9 — Python and Ruby's rules, inherited whole rather than invented. Earns its place beyond looks: Math.pow goes through doubles and can only return a Float, where 2 ** 10 gives the Int 1024. Overflow is reported, not wrapped. Not ^: every programmer reads that as XOR.
Keyword stylevar const func class traitRecognizable abbreviations of the words they mean. fun spells a different English word and buys a recurring question; fn is an abbreviation a student must be told about; function is eight characters on nearly every line of a class body.
Statement terminationNewline; no semicolon tokenNot optional semicolons — the token does not exist. Go permits them and then has gofmt strip them, which is two rules doing one job.
Line continuationTrailing operator, comma, open bracket; or next line starts . else then withThe leading-. rule is load-bearing: without it, multi-line method chaining breaks, and chaining is how §3.2 replaces the pipe operator.

3.2Types and semantics

DecisionFormDeciding argument
TypingStatic, inferredInference is not a second discipline — it is one discipline with the annotation omitted. The var objection does not apply.
Everything is an objectUniform surface, CLR representationThe requirement is that everything responds to . and no globals operate on receivers. That is surface uniformity, achievable while Int compiles to System.Int32. Kotlin's model.
The empty valuenothingSame logic as var and constructor — a word that is its own definition. "This holds nothing" is a complete explanation. null carries fifty years of baggage and means nothing to a fifteen-year-old, nil abbreviates a Latin word, none reads as a quantity. Surfaced by drafting an error message, not by the decision tables.
NullabilityNon-nullable by default, ? to opt inOne character, compiler-enforced, and maps onto C#'s nullable reference types for interop. Avoids teaching monads.
Using a nullableFlow-sensitive narrowingAfter if p != nothing, p is a Player inside the branch. Kotlin's smart cast, TypeScript's narrowing, C#'s nullable flow analysis. Non-negotiable — without it, non-nullable types are miserable to use. Teaches well: once you have checked, the compiler knows.
What narrowing producesThe stripped type, not "anything"The first implementation narrowed Player? to an unknown-but-not-null type. That is enough to reach .name, so the gap survived the whole nullability implementation unnoticed — it only surfaced when an operator had to find add on the narrowed value and there was no longer a type to find it on. Narrowing now produces the real Player. A reminder that "the tests pass" and "the type is right" are different claims.
Fallbacks.or(default), .value()Methods, not operators — discoverable by typing ., chainable, no cryptic sigil. ?? was rejected for the same reason as the ternary. Compiler intrinsics, since a null reference cannot dispatch, but indistinguishable from methods to the reader. .or(x) is exactly if v != nothing then v else x, so narrowing is the primitive and this is the convenience — §2.1 in miniature.
No ?.Rejected for v1Collides with §3.4's predicate ?. Fails silently — a beginner writes p?.name, gets nothing, and never learns the branch did not run, which inverts §2.6. And C# needs it because its entire BCL is nullable; Emerald's own types are not, so deep nullable chains should be rare by construction. Adding it later is backward compatible (§2.5).
Where to stopNo .map, .and_then, .filterOnce .or() exists these are easy, and they are the road to a full Option API — precisely the complexity rejected when ? was chosen over option types. .or() and .value() earn their place by being what a beginner reaches for. Held until real demand argues otherwise.
Throwing and catchingthrow, try { } catch e { }The syntax for the row below, which had been settled for months with no way to use it. catch is required — a try that swallows nothing does nothing, and one that swallows silently is worse. Untyped in v0; catching by type needs user-declared error classes first.
Runtime failures are catchableNot merely avoidableA catch handles both a thrown value and the interpreter's own errors, so "banana".to_int() can be recovered from rather than only sidestepped with to_int_maybe. Deliberately does not catch exit or a return unwinding through: neither is a failure.
throw "oops"Shorthand for throw Error("oops")A spelling, not a second concept, so §2.2 makes it free. Throwing anything else — an Int, an instance — is an error naming both forms.
ErrorsExceptionsThe CLR has first-class IL support and every .NET library throws. Result types would mean wrapping every interop call — fighting the platform on its home turf.
Mutabilityvar mutable, const immutableBoth words are their own definitions — a variable varies, a constant does not. let was considered and rejected: in math it declares a fact that holds, which is immutable semantics, so let-as-mutable borrows the familiarity while inverting the meaning. Does not reopen the C# objection — that was about int x and var x coexisting; here there is only one form.
Reuse modeltrait, single class inheritanceOne concept covers interfaces and abstract classes: an interface is a trait implementing nothing. Lowers to CLR interfaces with default methods, a real runtime feature since .NET Core 3.0. Single inheritance is forced by the CLR and is the right answer regardless.
Trait stateNone; traits declare what they requireCLR interfaces cannot hold fields, so traits cannot either. Treated as a feature — a trait names its dependency as an abstract member instead of stashing hidden state in you, which is how Ruby modules become unexplainable.
AbstractnessInferred from unimplemented membersNo separate abstract class declaration. Yields a teachable diagnostic — "Cannot create Animal — speak has no implementation" — rather than C#'s "you forgot to also mark the class."
Array literal inferenceThe narrowest shared typeFound by building inheritance: [rex, tweety] must infer Array<Animal>, not fail because a Bird is not a Dog. "First item wins" sufficed until subclasses existed, which is why the gap stayed invisible through the whole array implementation.
self is not a keywordAn ordinary bindingA method's scope simply contains self, so self.name is plain member access. No AST node, no parser case, no special handling in the checker or interpreter — the feature costs one line at each call boundary and nothing anywhere else.
Field accessself.name requiredApplies the author's own classroom finding: students identify variables in JavaScript because let marks them and struggle in Python where nothing does. self. is that marker for state. Five characters for a distinction otherwise held in the head.
Visibility_name, compiler-enforced; one levelZero keywords, and visible at the use site rather than only the declaration. Go's capitalization trick is unavailable — §3.4 already spends case on the type distinction. _ means internal to the class and its subclasses, collapsing C#'s private/protected. Accepted cost: changing visibility is a rename. A stricter level can be added later without breaking anything (§2.5).
Constructorconstructor; called as Dog("Rex")Frequency governs abbreviation: var and func appear on every line and are worth shortening; a constructor appears once per class, so length is nearly free and should be spent on clarity. constructor is the word students are taught for the concept — zero translation. init abbreviates jargon into more jargon; initialize is Ruby's but pairs with Dog.new, so you write one word and call another; the class name brings Java's rename hazard and a grammar special case. No new at the call site — construction is a call.
OverloadsPermitted, with defaultsType-based dispatch is what default values cannot do, so both earn their place.
RedefinitionAn error until overloads existTwo functions of one name previously overwrote each other in silence, so calls to the first went somewhere else with no warning — the worst possible handling. Rejected now, naming the first definition's line. The row below describes the eventual behaviour; this is what happens until it exists.
Overload ambiguityRejected at declaration, not at the callC# resolves at the call site with subtle rules, and its own guidance is to avoid mixing optional parameters with overloads — a language advising against its own feature. Overlap is decidable here (finite arity, static types), so the error lands on whoever created it: "greet already has an overload matching this one once defaults are applied."
PropertiesA var with a get / set bodyNot a separate feature. A var without a body is a field; with one it computes; the call site cannot tell, so promoting a field to a property never breaks callers. C#'s { get; set; } boilerplate exists only because C# keeps fields and properties distinct — collapse the distinction and the boilerplate has nothing to do.
Operator overloadingVia traits, lowering to named methodsa + b calls a.add(b), with Addable as the contract — Rust's std::ops model. Answers the question Python's dunders answer, using a mechanism that already exists. Operators stay discoverable by typing . because they are ordinary methods. Overloadable set kept small: arithmetic, Equatable, Ordered, Indexable.
The operator traitsAddable/add, Subtractable/subtract, Multipliable/multiply, Divisible/divide, Equatable/equals?, Ordered/compareBuilt, and shipped as a prelude: six ordinary trait declarations written in Emerald that the compiler prepends to every program. Synthesising them in C# would have been the same amount of code and would have created a second path through trait resolution for the built-ins to hide bugs in — this way a defect in traits breaks the operators too, loudly. equals? carries the ? because §3.4 requires it of anything returning Bool; a built-in that violated the rule the moment it was enforced would be an odd thing to ship. %, ** and // stay numeric-only — "kept small" has to bite somewhere, and no one has asked what a user type's remainder means.
One compare, four operators< > <= >= all read its signNegative, zero, positive. Four separate methods could disagree with one another — a type where a < b and a >= b are both true is a bug no reader would think to look for. Same reasoning as != always being the negation of equals? rather than separately definable.
== without EquatableIdentity, not an errorConsidered rejecting it, on the grounds that Java's ==-on-String is the classic footgun this language exists to remove. Ruled out by narrowing: x != nothing is the primitive that non-nullable types are built on, and it has to type-check for every x. So == stays total, and a type that has not said what sameness means answers the honest question instead — whether these are the same object.
String orderingBuilt in, ordinal"apple" < "banana" needs no trait. It is the one comparison a beginner reaches for that has nothing to do with arithmetic, and it failed until operator overloading landed. Ordinal rather than culture-aware, so a program sorts identically on every machine — .NET's culture-sensitive default makes "a" < "B" depend on the operating system's locale.
Type redefinitionAn error, naming the first lineTwo types of one name silently overwrote each other, exactly as two functions once did. Found by building the prelude: a program declaring trait Addable would have replaced the built-in one and broken + with a diagnostic pointing nowhere near the cause. The prelude names get their own message, since "already defined on line 4" would point into a file the programmer has never seen.
StringsSystem.String; no integer indexingBeing System.String keeps interop free. Grapheme indexing would be correct but O(n) wearing O(1)'s syntax, and for i in 0..s.length { s[i] } is then quietly quadratic — in a TUI library, that is the whole workload. Swift hit this and removed integer indexing rather than document the trap. Iteration yields graphemes; .chars is one visible O(n) conversion to an O(1) array; .code_units and .code_points sit underneath.
Type-level membersstatic func, static varKept despite being the one keyword here that names a storage strategy rather than a concept. shared was considered — VB.NET's choice, and it states the observable truth (one variable shared by every instance, against var name where each gets its own) — but static is what students will meet in every other language, and the transfer is worth more than the accuracy. The call site needs no help either way, since §3.4 casing already separates dog.speak() from Dog.from_shelter_id().
Why a keyword at allInference and explicit receivers both rejectedInferring from "never touches self" is decidable and a trap: adding one self. later silently converts a type method to an instance method and breaks every caller. Python's explicit self parameter marks the 95% case to leave the 5% case unmarked — the wrong trade, and its most-criticized wart. The _ trick does not transfer: private members are common and the marker is one character; type-level members are rare.
Modules and staticsNo keyword inside a module fileA file with a class line is that class's body, so func is an instance method. A file without one is a module, which has no instances — every func there is static already, so the keyword would be noise and is disallowed.
Free functionsPermitted; become static methods on the file's classNo new mechanism — §3.3 already compiles a file to a class. math_utils.em's clamp is MathUtils.clamp elsewhere, so every function has a home namespace and Emerald has no true globals. The receiver is implicit, not absent, so all-objects holds.
Value semantics need no implementationImmutability makes copying unobservableConfirmed by building it. Structs are enforced immutable — only a struct's own constructor may write its fields — and copy-on-assign was never implemented, because copying an immutable value is indistinguishable from sharing it. The row below argued this in the abstract; it turns out to be an implementation strategy, not just a teaching argument.
Value typesstruct, always immutableC#'s value/reference model, minus C#'s worst footgun. Mutable structs are what make transform.position.x = 5 fail; if they cannot be declared, that bug cannot be written. Value semantics are only observable under mutation, so students meet structs when they want the stack allocation and never get bitten first.
Iterationfor x in items lowers to iterator protocolAdopting .NET's IEnumerable makes every existing .NET collection work with for at zero cost.
Lambdasx => expr, plus trailing-lambda sprinkleTrailing lambdas give Ruby's block feel for one grammar rule. Parameter names explicit for now — implicit it is addable later, not removable (§2.5).
How a lambda produces a valueOne expression, or an explicit returnSurfaced by building the interpreter: items.filter { p => p.active? } must yield something, but { p => return p.active? } is unwritable. Resolved the same way if / then was — a single-expression form carries the value, so blocks never need value semantics and §3.2's explicit return survives. One principle applied twice rather than two unrelated rules. A block-bodied lambda whose value is used but which never returns is a checker error, not a silent nothing.
return inside a lambdaReturns from the lambdaNot Ruby's non-local return, which exits the enclosing method and surprises everyone exactly once; Kotlin needed return@label to escape the same choice. A student reading { p => ... return x ... } assumes it returns from the block in front of them, and the language should agree. Mostly moot in practice: single-expression lambdas contain no return at all.
MetaprogrammingCompile-time onlyRuntime dynamism is what defeated Ruby's tooling — not expressiveness. Renouncing it keeps the LSP and costs almost nothing.
Conversions.to_int() / .to_int_or(0)Chaining is discoverable by typing .. A conversion spelled Integer("42") is shaped like construction but means parsing.
PipelinesMethod chaining; no |>In an all-objects language the receiver is the pipeline. Elixir needs |> because free functions nest inside-out; Emerald does not.

3.3Program structure

DecisionFormDeciding argument
Entry pointTop-level statements, every fileNon-negotiable requirement. Stricter than C#, which permits them in one file with subtle adjacent rules — the two-disciplines smell again.
File semanticsA file is a module; runs top to bottomMatches the model students already hold. Compiles to a class with a static method; the entry file's is the assembly entry point.
Top-level variablesModule-level, not method localsLets functions in a file see them without Python's global wart. Accepts some global-state hazard to keep the rule free of asterisks.
Kernel membershipprint read_line random exitexit was added after a real program needed it: a validation failure printed a message and then carried on, because there was no way to stop. Found by the user writing a guessing game, not by design review — which is the §3.7 admission rule working as intended.
read_line at end of inputThrows, rather than returning ""Returning an empty string surfaced later as "" is not a number from whatever parsed it — an error about the wrong thing, several lines from the cause. Returning String? would be correct but puts .or("") on the most-used function in a beginner's program. Throwing names what actually happened.
Core functionsKernel, callable bare or qualifiedprint(x) and Kernel.print(x) both work, so the one un-explorable namespace becomes explorable by typing Kernel..
Class declarationBlock-free at file levelclass Dog extends Animal with Swimmer on its own line; everything below is the body. Removes an entire nesting level from every file, which is the whole reason GDScript reads light.
Why not filename-as-typeRejectedGodot's model, but it removes the type name from the file: class Dog greps to nothing, renaming a file silently renames a type, and the name lives somewhere other than where the reader is looking. Godot ships class_name for the same reason.
A module is a class with no instancesConfirmed by building itA file declaring no type becomes a type named after the file, with every member static — so math_utils.em is reached as MathUtils.clamp(...). This needed no new mechanism at all: the module story is the class story with one flag set, which is why the row below could promise "no true globals" without inventing anything.
Imports within a projectNone required, everSame directory is visible unqualified; other directories are reached by path (Shapes.Dog) with no import statement; import shapes is an optional sprinkle to drop the qualification. A student never writes an import. Java and Go require one for everything, which is ceremony in the common case; C# added implicit usings because the ceremony was not earning its keep.
External packagesimport raylib requiredA genuine dependency is worth declaring. The distinction is meaningful rather than bureaucratic: inside the project, nothing; outside it, one line.
NamespacesThe directory treePath maps straight to .NET namespace with the project as root, so Shapes.Dog is MyGame.Shapes.Dog in IL and reads correctly from C#. Nothing to keep in sync — no namespace line that can disagree with the folder containing it.
Import side effectsStructurally almost impossibleType files (class/trait/struct) have no top-level statements to run, so importing one executes nothing. Only module files can, and their top-level code runs once on first member access — a CLR static constructor, so the lowering is free and Python's import-order problems do not arise.
Block scopingEvery block is a scope; nothing leaksA var declared inside an if or a loop is gone afterwards. Ruby's for leaks its variable into the enclosing scope, which was noted as a defect back in §3.1 and is not inherited.
Loop variablesFresh each iterationClosures made inside a for capture 1, 2, 3 — not 3, 3, 3. The classic closure-in-a-loop bug, which JavaScript needed let to fix and C# changed foreach in version 5 to avoid. Confirmed by test, not assumed.
HoistingFunctions yes, variables noUsing a var before its declaration is an error; functions are visible anywhere in the file. Without function hoisting, mutual recursion needs forward declarations — exactly the ceremony §3.3 exists to remove. The checker and interpreter must agree on this: they briefly did not, and the result was a program the type checker accepted and the runtime rejected.
ClosuresCapture by reference(1..4).each { n => total += n } updates the outer total. The environment is shared, not copied.
ShadowingError within a function; fine across oneC#'s rule. var x inside a block when an x is already visible is almost always a student meaning to change it, so the diagnostic says exactly that rather than "already declared". Crossing a function boundary is allowed, so a local count is legal beside a module-level count, and a block parameter may shadow an outer name. An error rather than a warning: it is nearly always a bug, the fix is one word, and warnings get ignored.
Entry pointmain.em by convention; or named explicitlyemerald run finds main.em; emerald run foo.em runs that file. Zero configuration for students, scripts still work.
A file has one of two shapesOne block-free type, or only block formsCorrects a contradiction the grammar exposed: if a block-free body runs to end of file, a later class X { } is nested, not a sibling. Resolved toward the simpler rule — the body runs to EOF with no exceptions, so nested is what you get, and nested helper types are useful. A sibling type goes in its own file, which §3.3 already encourages, or the file uses block forms throughout. Two shapes but not two disciplines (§2.2): the same declaration with its body implied or written, exactly as top-level statements relate to an explicit Main.

3.8Metaprogramming

DecisionFormDeciding argument
Two features, not oneAttributes ≠ macrosSettles the old "attribute responsibilities" question. Of four harvested demands, three generate no code at all — @export attaches a .NET attribute, @external suppresses a diagnostic, @name overrides emitted metadata. Only assert is a macro. They were never one mechanism.
AttributesFixed vocabulary, v1@export, @test, @external, @name. Declarative, compiler-known, no user extension initially. Ships early because they are needed early, and each is roughly ten lines rather than a subsystem.
Macros, v1Function-like, expression positionCovers assert, which is the only harvested demand that needs real code generation. Crucially it needs no way to add members to a type, so the whole partial-class question does not arise yet.
Additive onlyNever transformativeTransformative macros are how Rails became unexplainable — has_many generates methods you cannot find. Deferred tierAttribute macros that add membersWhere the hard parts arrive together: a partial mechanism (or generation into a trait), full syntax-context hygiene, and phase ordering against name resolution. Genuinely difficult — and genuinely later.

Where DSL feel comes fromMostly not macrosA refinement of §2.3. What makes the Unity sample read like GDScript is the block-free class line, trailing lambdas, inference, func, and snake_case — settled language features. The only metaprogramming is @export, an attribute alias. The load is distributed across work already done, which is why the hard tier can arrive late without stranding the thesis.

4.1One mechanism, three spellings

All three compile to the same iterator protocol. Teach the first; the others need no new concept. This is §2.1 and §2.2 made concrete.

for i in 1..5 {
    print(i)
}

(1..5).each { i => print(i) }

1.upto(5) { i => print(i) }

The same economy in conditionals. if is an expression, so there is no ternary to learn and no declare-then-assign dance — and construction is a plain call, with no new.

            else if score >= 80 then "B"
            else "C"

var rex = Dog("Rex")

And the expressive one-liners — each one replacing arithmetic or a loop with something that reads aloud. These exist only because everything is an object: 5.times requires Int to have methods.

4.2The object model

Traits carry implementation and state requirements; classes inherit one base and mix in any number of traits. An interface is not a separate feature — it is a trait that implements nothing.

animal.em
class Animal

var name: String
var _chip_id: Int              # internal, enforced

constructor(name: String) {
    self.name = name
}

abstract func speak(): String

func introduce(): String {
    return "#{self.name} says #{self.speak()}"
}
swimmer.em
trait Swimmer

abstract func stamina(): Int   # the trait requires this of you

func swim() {                   # the trait provides this to you
    print("Swimming for #{self.stamina()} minutes.")
}
dog.em
class Dog extends Animal with Swimmer

static var total_count = 0    # one, shared by every dog

static func from_shelter_id(id: Int): Dog {
    return Dog(lookup_name(id))
}

func speak(): String {
    return "Woof"
}

func stamina(): Int {
    return 30
}

Properties are not a separate construct — a var with a get body computes, one without is a field, and callers cannot tell which. Operators are ordinary methods reached through a trait.

circle.em
class Circle

    get { return PI * self.radius * self.radius }
}

struct Vector3 with Addable

# a + b lowers to a.add(b)

What the design is ultimately aimed at. Left is Unity's C# today; right is the same behaviour with Emerald's decisions plus a wrapper library. Nothing on the right requires a feature not already settled above.

§ 5Platform constraints

Targeting CIL buys generics, exceptions, garbage collection, and the entire BCL. It also imposes requirements that are not negotiable, and are cheaper to design around now than to discover later.

5.1The runtime must be AOT-friendly

Most Unity build targets convert IL to C++ ahead of time via IL2CPP, which forbids runtime code generation. Emerald's runtime must therefore be fully static — no Reflection.Emit, no runtime dynamism. This costs nothing, because §3.2 already renounced runtime metaprogramming, but it converts a preference into a hard requirement.

5.2Subclassing .NET types is the litmus test

An Emerald class must be able to inherit a C# class and override its virtual methods with correct IL, such that the C# side calls back into Emerald. extends Behaviour is exactly this. It is the single most important interop capability, and the right first target once a CIL backend exists — if it works, most of the roadmap is reachable.

5.3Generics: consuming is mandatory, declaring is not

Touching .NET at all means calling List<T>, Dictionary<K,V>, and Task<T>. Letting users declare generic types can be deferred for years — Go managed a decade by reserving generics for the compiler. The CLR reifies generics rather than erasing them, so the implementation is inherited from the platform rather than built.

5.4Unity integration — verified feasible

Unity compiles C# in Assets/ with its own toolchain, so Emerald cannot be a script language there. The path is precompiled assemblies, and it is documented rather than folklore: a managed DLL dropped into Assets gets a foldout in the Project window revealing its classes, and MonoBehaviour subclasses can be dragged onto GameObjects exactly like ordinary scripts. Compiling against the Unity API means referencing Unity's own DLLs from the editor install. Target framework is .NET Standard 2.1 for Unity 6 today — but see the CoreCLR note below, which supersedes this. Documented gotcha: a .dll sharing a filename with an .asmdef hides its MonoBehaviours from Add Component.

IL2CPP's restrictions land exactly where §5.1 predicted. System.Reflection.Emit is deliberately unimplemented; also unsupported are dynamic, runtime generic construction via Activator.CreateInstance with MakeGenericType, generic virtual functions not inferable at compile time, and code reachable only through reflection, which stripping may remove.

The nuance that matters: merely referencing Reflection.Emit fails the build, used or not. That splits the architecture cleanly — the compiler may use it freely, since it runs at build time and is never shipped (Mono.Cecil is the better choice anyway and sidesteps the question); the runtime library inside the DLL must not reference it at all.

The design had already paid for this

No runtime metaprogramming, compile-time expansion only, static dispatch, traits lowering to interface default methods rather than runtime-constructed generics — every one of those was chosen for tooling or teachability, and every one is what IL2CPP requires. Nothing was spent on Unity compatibility that had not already been spent.

And IL2CPP is a shipping concern, not a teaching one. Desktop builds can use a JIT backend when the restricted features are needed; IL2CPP is required for iOS, WebGL, and consoles. A classroom building Windows executables is unconstrained by any of the above.

CoreCLR changes the target, not the blocker. Unity is replacing the scripting runtime through 2026 — 6.7 LTS ships an experimental CoreCLR desktop player, 6.8 drops Mono entirely, bringing the .NET 10 BCL and C# 14. This does not affect the compilation pipeline, so the precompiled-assembly path remains the path. But it means the JIT escape hatch above will be CoreCLR rather than Mono — more capable, since Reflection.Emit works under a JIT runtime.

It also settles the target framework question. Emerald will not have a CIL backend for years, and CoreCLR becomes Unity's foundation in 6.8, so the timelines align: design for modern .NET and skip netstandard2.1 rather than carrying compatibility baggage for a world that is ending. One to watch, not to plan on: the migration moves assembly loading to AssemblyLoadContext, the mechanism behind unloading and hot reload in modern .NET. If that reaches plugin assemblies, the reload problem below softens considerably.

What remains is ergonomics, not capability. No hot reload — rebuild the DLL and wait for Unity's reimport, which is still a real regression from edit-save-play and the biggest classroom risk. No editor integration: no "Create > Emerald Script", no double-click-to-open. And debugging requires portable PDB emission so breakpoints map to .em files — well-documented but real work, without which stack traces point at IL and debugging is effectively unavailable.

Godot 4 supports .NET and likely makes the assembly path smoother still. The objection to Godot is conceptual — nodes versus GameObjects — and a wrapper is exactly what resolves a conceptual objection. The door remains open.

Not yet decided. Ordered roughly by how much each constrains everything downstream.

§ 7Implementation roadmap

Sequenced so that each phase produces something usable, and so that the parts most likely to be invalidated by external constraints come last.

Phase 0

Learn the craft

Work through Crafting Interpreters. The front half — scanning, parsing, AST, resolution — is identical regardless of backend, and transfers completely. The back half teaches stack-based bytecode execution, which is what CIL is.

Outcome — vocabulary and a working mental model

Phase 1

Tree-walking interpreter in C#

Runs real Emerald programs within weeks rather than years. This phase is where the language's semantics actually get decided — designing IL emission before knowing the semantics is the classic way to stall.

Outcome — a running language, and a REPL almost for free

Phase 2

CIL backend

Swap the backend once the language is known. First milestone is §5.2 — an Emerald class subclassing a C# class correctly. Mono.Cecil is preferable to Reflection.Emit: it writes assemblies to disk and keeps the shipped runtime clear of a namespace IL2CPP rejects on sight (§5.4). Target modern .NET, not netstandard2.1 — Unity's CoreCLR migration lands well before this phase does. Portable PDB emission belongs here too, or debugging never works.

Outcome — real assemblies, real .NET interop, working breakpoints

Phase 3

Tooling

Formatter first — it is the smallest piece and the one §2.4 depends on most. Then the LSP, which the no-runtime-metaprogramming decision makes tractable.

Outcome — emerald fmt, then editor support

Phase 4

Libraries

A Spectre.Console-flavoured TUI library first: pure managed code, no native interop, and writable in Emerald — which makes it a dogfooding test, not just a demo. Then a small 2D framework over Raylib or MonoGame, which stays entirely under the author's control. Unity after that, because it is the only part someone else's toolchain can invalidate.

Then a GUI wrapper — a Tkinter or PySimpleGUI analogue rather than a WinUI or WPF replacement. Over Avalonia: cross-platform, already admired, and — the practical reason — it runs on Linux, which matters while the WSL workaround stands. Not WinForms, which is genuinely the closest thing .NET has to Tkinter but is Windows-only and a dead end.

Two things to steal, one to avoid. Take PySimpleGUI's polled event loop — while window.open? { var event = window.next_event() ... } is a while loop, which a student already understands, where Tkinter's callbacks demand event-driven thinking. Take block-based layout, which trailing lambdas already provide with no new syntax. Avoid rebuilding a widget toolkit; wrap one.

Why this order, beyond difficulty

The TUI is a rehearsal for the GUI: the same problems — layout, widgets, an event loop, a declarative block API — at a fraction of the surface and with no toolkit to learn. Whatever it teaches about making blocks read well transfers directly.

And a GUI is arguably the strongest test of §2.3 available. Nested layout is the classic DSL case; if Window("Guessing Game") { label(...) button(...) { ... } } reads well, the claim that libraries can feel like language stops being a promise. The TUI proves it in one dimension, a GUI in two.

Known collision: a Windows GUI launched from WSL needs WSLg or an X server. Avalonia-on-Linux works under WSLg, but this is another reason to resolve the Smart App Control block properly rather than routing around it indefinitely (§5.4).

Outcome — TUI → 2D framework → engine wrapper → GUI

§ 8Learning path

The project's stated second purpose is to become a better programmer. That makes some inefficient choices correct.

Build the interpreter by hand. It is the phase that teaches the most per hour, and skipping it to reach a "real" compiler faster would forfeit the point of the exercise.

Compile-time metaprogramming deserves study time now. §2.3 makes it load-bearing rather than optional. Rust's macro system and C#'s source generators are the two nearest reference implementations, and it is the least-specified part of the design.

Learn to read IL before writing it. Inspecting what the C# compiler emits for a class, a property, and a virtual override is the fastest route into Phase 2 — and it is reading, not building, so it can start any time.

On scope

Every phase before 4 produces something that works and teaches something durable. If the project stops after Phase 1, the outcome is a working language, a REPL, and a genuine understanding of how languages are built. That is a good outcome, not a failed one — worth writing down before the ambition of Phase 4 makes it feel otherwise.

§ 9Grammar

The artifact between a decision list and a parser. Writing it was how three conflicts surfaced — the modifier-if line rule, the trailing-lambda ambiguity in conditions, and the block-free class contradiction. All three are now settled in §3 and reflected below.

Emerald — core grammar
file            = block_free_file | block_file
block_free_file = type_header NEWLINE { member }
block_file      = { { attribute } declaration }

type_header     = ( "class" | "trait" | "struct" ) Ident
                  [ "extends" Type ] [ "with" Type { "," Type } ]

declaration     = type_block | member
type_block      = type_header "{" { { attribute } member } "}"

member          = func_decl | var_decl | const_decl | ctor_decl | type_block
func_decl       = [ "static" ] [ "abstract" ] "func" method_name
                  "(" [ params ] ")" [ ":" Type ] [ block ]
method_name     = Ident [ "?" ]
var_decl        = [ "static" ] "var" Ident [ ":" Type ]
                  [ "=" expr | property_body ]
property_body   = "{" [ "get" block ] [ "set" block ] "}"
const_decl      = [ "static" ] "const" Ident [ ":" Type ] "=" expr
ctor_decl       = "constructor" "(" [ params ] ")" block

statement       = simple_stmt [ "if" cond ]   -- modifier: same line only
                | if_stmt | while_stmt | for_stmt
simple_stmt     = var_decl | const_decl | "return" [ expr ]
                | "throw" expr
                | assignment | expr
assignment      = postfix assign_op expr   -- statement, never an expression
assign_op       = "=" | "+=" | "-=" | "*=" | "/="
if_stmt         = "if" cond block
                  { "else" "if" cond block } [ "else" block ]
while_stmt      = ( "while" | "until" ) cond block
try_stmt        = "try" block "catch" Ident block   -- catch is required
for_stmt        = "for" Ident "in" cond block
block           = "{" { statement } "}"   -- never a statement itself

cond            = expr                    -- no bare trailing lambda

expr            = if_expr | or_expr
if_expr         = "if" expr "then" expr "else" expr
or_expr         = and_expr { "or" and_expr }
and_expr        = not_expr { "and" not_expr }
not_expr        = [ "not" ] comparison
comparison      = range [ ( "==" | "!=" | "<" | ">"
                          | "<=" | ">=" ) range ]
range           = additive [ ".." additive ]
additive        = multiplicative { ( "+" | "-" ) multiplicative }
multiplicative  = unary { ( "*" | "/" | "//" | "%" ) unary }
unary           = "-" unary | power
power           = postfix [ "**" unary ]   -- right-associative
postfix         = primary { "." member_name [ args ] [ lambda ]
                          | args [ lambda ]
                          | "[" expr "]" }
member_name     = Ident | Keyword   -- keywords are legal after '.'
primary         = literal | Ident | Type | array | "(" expr ")" | lambda
array           = "[" [ expr { "," expr } ] "]"

lambda          = "{" [ params "=>" ] { statement } "}"
args            = "(" [ expr { "," expr } ] ")"
params          = param { "," param }
param           = Ident [ ":" Type ] [ "=" expr ]
attribute       = "@" Ident [ "(" literal { "," literal } ")" ]

9.1What the three annotations carry

statement = simple_stmt [ "if" cond ], same line only. A newline before if starts a new statement, because if is not among the tokens that continue one (§3.1). Without this, a following if is ambiguous between a modifier and a fresh statement.

cond forbids a bare trailing lambda. Otherwise if x { ... } could attach the block to x as a trailing lambda rather than opening the if-statement's body. Kotlin resolves this identically.

block is never a statement. With no anonymous scopes, a { after an expression is unambiguously a trailing lambda.

assignment is a statement, not an expression. It cannot appear inside cond, so if x = 5 { } fails to parse rather than silently assigning — the C-family =-for-== bug removed structurally rather than warned about. The left side is postfix, which covers x, self.name, dog.score, and list[0].

Note also that if_stmt and if_expr are distinguished only by what follows the condition — { or then. A recursive-descent parser reads the condition, then peeks. No lookahead beyond one token past the condition is required.
